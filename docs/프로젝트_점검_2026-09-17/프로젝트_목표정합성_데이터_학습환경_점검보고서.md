## 1. 최종목표와 현재 프로젝트의 관계

### 유지할 수 있는 구성

현재 흐름은 `웹캠 → 얼굴 랜드마크 → 입술 ROI → WebSocket → 영상 모델 → CTC 디코딩 → 자막`이다. `getUserMedia({video:true})`를 사용하므로 웹캠 입력 경로는 음성을 요구하지 않는다. 입술 영상만으로 텍스트를 추론하려는 최종목표와 방향이 맞는다.

기존 구성에서 재사용할 수 있는 부분은 다음과 같다.

- React의 웹캠·업로드·결과 화면과 FastAPI/WebSocket 연결 구조.
- 96×96 RGB 입술 영상, 25fps, 정규화 규칙 등 입력 계약.
- AI Hub 문장 시작·종료 시간으로 클립을 만드는 코드와 라벨 입술 박스를 활용하는 ROI 추출 경로.
- 문장 길이에 따라 학습하고, 마지막 프레임으로 배치 패딩하는 처리.
- CTC 정렬 최소 길이 검사, 비슷한 길이의 배치 구성, gradient clipping.
- CTC 기반 문장 인식과 디코딩의 기본 틀.

전체 프로젝트를 폐기할 필요는 없다. 다만 UI와 통신 코드가 있다는 사실, 가중치 파일이 있다는 사실, 단위 테스트가 있다는 사실은 실제 립리딩 성능의 입증과 구분해야 한다.

### 2.1 한글 정답에서 겹받침과 공백이 사라짐 — 최우선

근거: [어휘 정의](C:/Users/HyunE/Desktop/lipnet_project/backend/models/__init__.py:10), [라벨 인코딩](C:/Users/HyunE/Desktop/lipnet_project/scripts/prepare_data.py:43), [음절 복원](C:/Users/HyunE/Desktop/lipnet_project/backend/models/decoder.py:39).

현재 41클래스는 초성에 쓰는 자음 19개, 모음 21개, CTC blank로 구성된다. `ㄳ ㄵ ㄶ ㄺ ㄻ ㄼ ㄽ ㄾ ㄿ ㅀ ㅄ`가 없고, 공백도 없다. 인코더는 어휘에 없는 글자를 조용히 버린다.

| 원래 정답 일부 | 저장된 라벨을 복원한 결과 일부 |
|---|---|
| 나이가 **많다고** | 나이가**마다고** |
| 인상은 **없었어** | 인상은**어었어** |

또한 문장 전체에서 공백과 구두점이 제거된다. 공백 없는 출력과 공백으로 나누는 WER 평가가 맞지 않는다. 더 많은 데이터를 학습해도 현재 출력 어휘에 없는 문자를 원래대로 출력할 수 없다.

권고: 초성·중성·종성을 구분하는 가역적인 토큰 체계를 정하고, 띄어쓰기 토큰과 숫자·영문·구두점 정규화 규칙을 문서화한다. 예를 들어 초성 19·중성 21·종성 27에 공백과 blank를 추가하는 체계를 검토할 수 있다. 정답→토큰→정답 복원 검사를 먼저 통과시킨 뒤 캐시 라벨을 새 버전으로 생성해야 한다. 출력 클래스 변경 시 기존 41클래스 체크포인트를 그대로 호환된다고 처리하면 안 된다.

### 2.4 웹캠의 시간축이 학습 조건과 다름

근거: [프레임 루프](C:/Users/HyunE/Desktop/lipnet_project/frontend/src/pages/WebcamPage.jsx:181), [청크 시간값](C:/Users/HyunE/Desktop/lipnet_project/frontend/src/pages/WebcamPage.jsx:167).

학습은 25fps이지만 웹캠은 `requestAnimationFrame` 호출마다 영상을 처리한다. 실제 새 카메라 프레임인지 확인하지 않고 25fps로 리샘플하지도 않는다. 디스플레이 갱신률·기기 성능에 따라 중복 프레임과 시간 간격 차이가 생길 수 있다. 청크 시작·종료 시간은 모두 0이다.

권고: 실제 영상 프레임의 타임스탬프를 수집해 25fps 타임라인에 맞춘다. 발화 종료 판단도 실제 경과 시간과 대응시킨다. 발화가 시작되기 직전의 짧은 ROI 버퍼를 유지해 첫 음절이 잘리지 않게 한다. 현재는 시작 조건을 통과한 프레임 다음부터 ROI를 모은다.

### 2.5 모델이 크고 웹캠 추론은 CPU에서 매 프레임 반복됨

근거: [LSTM 입력 크기](C:/Users/HyunE/Desktop/lipnet_project/backend/models/baseline.py:53), [CPU 로드](C:/Users/HyunE/Desktop/lipnet_project/backend/models/baseline.py:125), [웹캠 추론](C:/Users/HyunE/Desktop/lipnet_project/backend/services/ws_handler.py:76).

CNN 출력의 공간축을 줄이지 않고 펼쳐 LSTM에 프레임마다 55,296차원을 넣는다. 소스의 레이어 형상으로 계산한 학습 파라미터는 **115,699,849개(약 1억 1,570만 개)**이며, 첫 LSTM 층이 약 98.3%를 차지한다. FP32 가중치만 약 441MiB이고, 가중치·gradient·Adam의 두 모멘트만으로 약 1.72GiB가 필요하다. 활성값, 역전파 임시 공간, CUDA 작업 공간은 별도다.

학습 코드는 CUDA를 자동 선택할 수 있지만, 웹캠·업로드 추론 코드는 모델과 입력을 CUDA로 옮기지 않는다. 브라우저 MediaPipe의 `delegate:'GPU'`는 백엔드 PyTorch GPU 사용과 별개이다. 웹캠 서버는 프레임을 받을 때마다 발화 전체를 다시 추론하고, 이를 비동기 수신 함수 안에서 동기 실행한다. 발화가 길어질수록 반복 계산과 응답 대기가 커진다. 현재는 설명과 달리 길이가 제한된 슬라이딩 윈도우도 아니다.

권고: 시간축을 유지하면서 공간 특징을 pooling/projection으로 줄이는 모델을 먼저 비교한다. 또는 사전학습된 영상 특징 추출기를 활용한다. 특징 차원 변경은 새 모델 버전과 재학습이 필요하다. 서버에는 명시적인 장치 선택, 청크 단위 추론, 길이 제한, 작업 큐와 오래된 중간 요청 처리 정책을 둔다. BiLSTM을 유지하면 확보된 구간을 다시 처리하는 방식의 자막이며, 미래 프레임을 전혀 기다리지 않는 스트리밍 모델과 구분해야 한다.

### 2.6 평가 API는 실측 결과가 아님

근거: [더미 평가](C:/Users/HyunE/Desktop/lipnet_project/backend/api/evaluation.py:75), [평가 스크립트](C:/Users/HyunE/Desktop/lipnet_project/scripts/evaluate.py:223), [비어 있는 평가셋 등록](C:/Users/HyunE/Desktop/lipnet_project/backend/config.py:85).

API는 실제 추론 없이 CER·WER·지연·검출률을 모두 0.0으로 기록하고 완료 처리한다. 별도 CLI 평가 스크립트에는 계산 코드가 있지만 API와 연결되어 있지 않다. 이 0.0을 정확도 100% 또는 지연 0ms로 해석하면 안 된다.

추가로 CLI의 지연은 업로드 영상 전체의 전처리·추론 시간이고, 웹캠에서 발화가 끝난 뒤 자막이 확정되는 시간과 다르다. 검출률도 한 영상 안에 검출 성공 세그먼트가 하나라도 있는지를 세므로 프레임 기준 검출률과 다르다. `eval_unit`은 결과 메타데이터에만 쓰이고 계산 단위를 바꾸지 않는다. CER/WER는 문장별 비율의 단순 평균이다. 논문과 비교할 때에는 토큰화, 공백 처리, corpus 단위 합산 여부를 맞춰야 한다.

권고: 독립 평가셋을 등록하고 실제 추론을 연결한다. 자모 CER·음절 CER·어절 WER의 정의를 명시한다. 웹캠에서는 발화 종료→최종 자막의 지연, 첫 중간 자막 지연, 평균과 p95, 프레임 누락률을 따로 측정한다. 현재 confidence는 프레임별 최대 확률의 기하평균이므로 “문장이 맞을 확률”로 표시하지 않는다.

### 2.7 긴 업로드 영상이 RAM을 소진할 수 있음

근거: [전체 프레임 로드](C:/Users/HyunE/Desktop/lipnet_project/backend/preprocessing/resampler.py:19), [전처리 목록 구성](C:/Users/HyunE/Desktop/lipnet_project/backend/preprocessing/pipeline.py:60).

영상 전체의 원본 프레임을 메모리에 넣은 뒤 분할한다. 1920×1080, 30fps, 180초, 3채널 uint8 영상은 원본 프레임 배열만 약 **31.3GiB**다. 현재 RAM 약 32GiB에서 다른 프로그램과 후속 복사·텐서가 함께 존재하므로 위험하다. 500MB 업로드 제한은 압축 파일 크기여서 이 메모리 문제를 막지 못한다.

권고: 순차 디코딩→필요 프레임 리샘플→ROI 추출→구간 처리→해제 방식으로 바꾼다. 학습 준비의 bbox 경로처럼 처리 범위를 제한하는 접근을 업로드 추론에도 적용한다.

### 2.8 추가로 정리할 일

- V-VAD 랜드마크에는 내측 상단·하단과 외측 점이 섞여 있다. `VVAD_IDX_TOP`에 하단 중앙 14가 포함되고, `VVAD_IDX_BOT`의 17·84·181·314는 외측 입술 경계다. [MediaPipe 공식 연결 정의](https://raw.githubusercontent.com/google-ai-edge/mediapipe/master/mediapipe/python/solutions/face_mesh_connections.py)와 대조하여 재정의하고, 입을 다문 상태·발화·웃음·고개 움직임으로 검증해야 한다. 정규화 x·y 거리를 섞을 때 영상 종횡비도 보정한다.
- 웹캠은 `numFaces:1`과 `faces[0]`을 쓰므로 사용자가 원하는 상대방을 선택·고정하는 기능이 없다. 먼저 “화면 안의 정면 화자 1명”을 운영 조건으로 명시하고, 여러 명 지원은 얼굴 선택과 추적으로 확장한다.
- 학습은 가변 길이 문장인데 파일 추론은 고정 3초 경계로 잘라 문장 중간을 끊는다. 평가 시 문장 단위 결과와 실제 구간 자막 결과를 구분하고, 경계 중복 처리와 텍스트 결합을 설계한다.
- 현재 last-frame 패딩 길이가 BiLSTM에 전달되지 않는다. CTC에 원래 길이를 줘도 역방향 LSTM은 패딩된 뒤쪽 프레임을 볼 수 있다. 패킹·마스킹 또는 동일 길이 처리에 대한 검토가 필요하다.
- bbox와 MediaPipe에 같은 margin·크기를 쓰는 것은 유용하지만, 두 방식의 박스 위치·크기·회전·흔들림 분포까지 같다는 의미는 아니다. 동일 문장에서 두 ROI를 비교하고 실제 웹캠 방식으로도 검증해야 한다. 회전 자동 감지는 현재 관측 사례에 기반한 휴리스틱이다.
- `prepare_data.py`의 “torch 미import” 설명과 달리 `roi_extractor.py`를 통해 torch가 간접 import된다. 환경 분리 의도가 실제 의존성과 일치하지 않는다.
- 학습에 AMP, gradient accumulation, optimizer·epoch·RNG까지 복구하는 resume 기능이 없다. 현재 체크포인트에는 모델 가중치와 일부 구조 정보만 저장된다. 장시간 학습과 Colab 중단 복구 전에 보완한다.
- 패키지 버전이 대부분 고정되어 있지 않다. 검증된 CUDA/PyTorch/MediaPipe 및 프론트 패키지 조합을 기록해야 재현할 수 있다.

## 4. AI Hub 데이터는 적합한가

**적합하다.** 해당 데이터는 한국어 MP4 영상, WAV 음성, 전사와 얼굴·입술 박스 JSON을 제공한다. 영상 5,750시간·음성 1,150시간이며, 정면 A 영상은 1,150시간으로 안내된다. 입술 영상과 정답 문장을 사용하면 음성을 모델 입력으로 쓰지 않는 학습이 가능하다. 웹페이지에서 소개하는 활용 모델은 Audio-Visual 융합 구조이므로 그 모델의 성능을 현재 영상 전용 모델에 그대로 적용해서는 안 된다. [AI Hub 공식 데이터 소개](https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=538)

OLKAVS 연구진도 영상 전용 V-model 결과를 공개했다. 정면 평가 결과는 CER 26.64%, WER 47.89%이며, 이는 연구진의 모델·전처리·평가 조건에 대한 수치다. 현재 프로젝트의 예상 성능이나 보장치가 아니다. 입술만으로 일반 문장을 복원하는 문제의 난도를 보여주는 참고값이다. 사전학습 영상 특징 추출기도 사용하므로 현재 모델과 직접 비교하려면 조건을 맞춰야 한다. [연구진 공식 저장소](https://github.com/IIP-Sogang/olkavs-avspeech)

데이터 논문은 하나의 발화를 여러 각도에서 동시에 촬영했으며, 화자 ID로 train/validation/evaluation을 8:1:1로 나누었다고 설명한다. 논문상 공개 범위는 train과 validation이다. 따라서 영상 5,750시간을 전부 서로 다른 발화 시간으로 해석하거나, 공개된 독립 test가 당연히 있다고 가정하면 안 된다. 현재 제공 파일 목록은 승인 후 명세와 대조한다. 학습 세트 안에서 화자별 내부 검증셋을 만들고 공개 validation을 최종 평가로 고정하는 방안도 가능하다. [OLKAVS 논문](https://arxiv.org/pdf/2301.06375)

이 데이터는 스튜디오에서 정상적으로 발화한 영상이다. 일반 웹캠의 거리·화질·조명·자세에는 차이가 있으므로 실제 목표 환경에서 별도 검증이 필요하다. “소음없음”은 배경 소음 조건이며 “목소리를 전혀 내지 않고 입만 움직임”을 뜻하지 않는다. 사용자가 목표로 하는 것이 실제 무발성 입모양까지 포함한다면, 해당 조건을 따로 수집·평가해야 한다. 정상 발화를 마이크 없이 읽는 현재 목표에는 데이터 선택이 타당하다.

## 5. 대용량 데이터를 다루는 방법

학습 데이터 전체가 GPU 메모리에 들어갈 필요는 없다. 디스크에는 데이터가 저장되고, RAM과 VRAM에는 현재 처리하는 클립·배치만 올라가게 설계하면 된다. 다만 현재 업로드의 전체 프레임 로드와 큰 모델은 별도로 수정해야 한다.

권장 처리 순서는 다음과 같다.

1. **라벨과 파일 목록을 먼저 조사한다.** 화자·문장·각도·길이로 manifest를 만든다. 처음 N개 파일만 고르면 현재처럼 한 화자에 집중될 수 있다.
2. **정면 A와 여러 화자를 우선 확보한다.** 초기 웹캠 조건과 맞추고 다양한 화자의 발화를 포함한다. 필요한 영상+라벨을 선택하며 WAV는 영상 전용 입력에 필수는 아니다. 단, 서버의 압축 묶음 단위에 따라 선택 다운로드의 세밀함은 달라진다.
3. **화자 분할을 확정한 뒤 문장 단위로 전처리한다.** 시작·종료 시간을 이용하고 라벨 박스의 방향·범위·시간 정합을 확인한다. 박스 예시 이미지를 사람이 확인한 뒤 범위를 늘린다.
4. **원본 전체 프레임 대신 입술 ROI를 캐시한다.** 현재 96×96 RGB uint8 규칙을 유지하고, float32 정규화는 배치 로딩 시 한다. 캐시에는 원본과 전처리 버전의 추적 정보를 남긴다.
5. **처리 단위를 나눠 완료 기록을 남긴다.** 예를 들어 관리 가능한 용량의 묶음별로 다운로드·해제·변환·검증하고 진행 상태를 기록한다. 기존 파일이 있다고 무조건 완료로 보지 말고 크기·키·프레임 수·라벨·CTC 조건을 확인한다.
6. **장기 학습에는 디스크 I/O도 측정한다.** NPZ는 현재 규모에서는 사용 가능하다. 파일이 매우 많아지면 수백 MB~수 GB의 shard와 인덱스를 검토한다. 매번 모든 `frames`를 풀어서 길이만 구하는 현재 `clip_length` 대신 manifest의 길이 정보를 쓴다.
7. **캐시 검증 후 보관 정책을 정한다.** 원본, 압축본, 병합본, 캐시를 무조건 모두 유지하면 디스크를 빠르게 소모한다. 재다운로드 가능성과 필요한 증거를 확인해 보관 범위를 정하되, 이번 검토에서 원본 파일을 삭제하지 않았다.

AI Hub는 승인 후 API 다운로드와 분할 압축 파일 병합을 안내하고, Linux 또는 Windows의 WSL 이용을 안내한다. 선택한 압축 묶음을 복원하려면 그 묶음의 필요한 part를 모두 받아야 한다. 정면 영상만 필요하다고 분할 압축의 일부 part를 임의로 빼는 방식은 사용할 수 없다. 현재 `prepare_batch.py`는 이미 풀린 MP4와 라벨 tar를 처리하며, 다운로드·분할 병합까지 자동 수행하는 도구는 아니다. [AI Hub 다운로드 안내](https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=538)

### 용량을 판단하는 계산 기준

아래는 **압축 전 RGB uint8 배열의 계산값**이며 실제 MP4/NPZ 다운로드 용량이 아니다. 단위는 decimal MB/GB이다.

| ROI 데이터 규모 | 계산 용량 |
|---|---:|
| 25fps·96×96×3, 5초 클립 1개 | 약 3.456MB |
| 같은 길이 1만 개 | 약 34.56GB |
| 같은 길이 10만 개 | 약 345.6GB |
| 정면 영상 명목 1,150시간 전체 | 약 2.86TB |

문장 구간만 추출하면 전체 녹화 시간을 모두 저장하는 계산보다 줄어들 수 있고, 압축률도 내용에 따라 다르다. 반대로 float32를 디스크에 저장하면 uint8보다 기본 배열 용량이 4배가 된다. 정확한 원본 전체 용량은 승인된 파일 목록의 크기를 합산해야 하며 이번 검토에서는 이를 확정하지 않았다.

다운로드 공간에는 `분할 파일 + 병합 압축본 + 해제한 원본 + 생성한 캐시 + 체크포인트 + 작업 여유 공간`이 함께 필요할 수 있다. 예를 들어 50GB 분할 파일을 50GB 압축본으로 병합하면 해제 전부터 약 100GB를 차지할 수 있다. 현재 D 드라이브 여유만 보고 100GB 원본 묶음도 안전하다고 판단해서는 안 된다.

| 전체 데이터로 처음부터 장기 학습, 많은 비교 실험 | 단일 10GB GPU만으로 실용적인 기간을 보장하기 어려움. 측정 후 추가 GPU 자원 판단 |
| 최종 프로그램 실행 | 학습 서버와 분리 가능. 학습한 가중치를 로컬 서버에 배치 가능 |

초기 학습 권고:

- 라벨·분할 오류를 먼저 고친다.
- 소수의 짧은 **완전한 문장**으로 과적합 검사를 해 학습 경로가 정상인지 확인한다. 이 단계의 높은 점수는 일반화 성능이 아니다.
- 모델의 공간 특징 차원을 줄인 후 batch 1부터 측정하고 가능할 때 늘린다. 길이가 긴 문장을 단순 앞부분 자르기로 만들면서 원래 전체 문장 라벨을 붙이면 안 된다.
- 필요하면 AMP와 gradient accumulation을 구현한다. 이것은 현재 존재하는 CLI 옵션이 아니라 추가할 기능이다. CTC 수치 안정성을 확인하고 loss에 필요한 FP32 계산을 유지한다. [PyTorch 공식 AMP 예제](https://docs.pytorch.org/docs/2.14/notes/amp_examples.html)
- CUDA 동기화와 초기 준비 시간을 구분해 step 시간·최대 VRAM을 측정한다. `ceil(클립 수 / 실제 배치 크기) × step 시간 × epoch 수`에 평가·전처리 시간을 더해 총 시간을 추정한다. 현재는 실측이 없어 “몇 시간에 완료”를 제시하지 않는다.
- 모델·optimizer·epoch·best metric·토큰 사전·전처리 버전·분할 manifest 식별자를 저장하여 중단 후 재개할 수 있게 한다.

### Colab을 선택할 때의 조건

Colab은 보조 실험 자원으로 사용할 수 있지만, 무료·유료 일반 런타임의 GPU 종류와 제공량은 고정되어 있지 않다. 무료 실행은 이용 상황에 따라 최대 12시간까지이며 항상 12시간을 보장하는 것도 아니다. 대용량 데이터는 영구 저장소와 런타임 임시 디스크를 구분하고, 체크포인트를 런타임 외부에 저장해야 한다. Drive에서 수많은 작은 파일을 매번 읽기보다 처리 묶음을 런타임 디스크로 옮겨 사용하는 구성을 검토한다. [Google Colab 공식 FAQ](https://research.google.com/colaboratory/faq.html)

따라서 “Colab이면 현재 RTX 3080보다 항상 빠르다”거나 “무료 Colab으로 전체 학습이 해결된다”고 판단하지 않는다. 로컬에서 코드·데이터·평가를 정상화한 다음, VRAM 부족 또는 측정된 학습 시간 때문에 필요할 때 더 큰 GPU를 선택하는 순서가 적절하다. 국내 대학·연구실 GPU 서버도 선택지다.

AI Hub 공통 이용정책에는 AI 데이터의 국외 반출에 별도 합의가 필요하고, 승인 없는 제3자 열람·제공을 제한하는 조항이 있다. 따라서 해외 클라우드인 Colab/Drive로 원본이나 ROI 캐시를 올리기 전에 해당 데이터의 승인 조건과 국외 처리 허용 여부를 확인해야 한다. ROI로 잘랐다는 이유만으로 조건이 자동으로 사라진다고 판단하지 않는다. 개인 PC에서 승인받은 데이터를 학습에 사용하는 것과 해외 클라우드로 옮기는 것은 따로 판단할 사안이다. [AI Hub 공식 이용정책](https://aihub.or.kr/intrcn/guid/usagepolicy.do?currMenu=151&topMenu=105)

## 7. 권장 실행 순서와 완료 기준

| 순서 | 할 일 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 1 | 최종목표·촬영 조건·평가 단위 확정 | 웹캠 필수, 음성 미사용, 대상 화자·문장·지연 정의가 문서에 일치 |
| 2 | 겹받침·공백·숫자 토큰화 수정 | 정규화된 정답을 토큰화 후 손실 없이 복원 |
| 3 | 여러 화자 manifest와 독립 분할 | 화자와 동일 녹화 발화 그룹의 분할 간 중복 0 |
| 4 | 웹캠 청크·빈 최종·정지·25fps 처리 수정 | 보내진 발화 프레임이 누락 없이 최종 추론에 반영 |
| 5 | 모델 크기·GPU 추론·메모리 관리 개선 | 목표 길이에서 VRAM·RAM 측정, 무제한 누적 제거 |
| 6 | 소수 클립 학습 검사 후 여러 화자로 확대 | 정상 학습 확인 후 독립 화자 성능을 별도 기록 |
| 7 | 실제 웹캠 평가 | 학습에 쓰지 않은 사람의 발화에서 CER/WER·검출률·평균/p95 지연 기록 |
| 8 | 필요시 추가 GPU와 데이터 확장 | 로컬 측정치, 저장 공간, 데이터 이용조건을 근거로 결정 |

현재의 우선 작업은 **① 정답 표현의 손실 제거 → ② 데이터 누수 제거 → ③ 웹캠 전송·시간축 수정 → ④ 모델·평가 개선 → ⑤ 다화자 학습 확대**이다. 이 순서가 갖추어져야 데이터 양이나 GPU 자원을 늘린 효과를 정확하게 판단할 수 있다.
