# 공식 모델 전환 5단계 결과 — 서버에 OLKAVS 상주 워커 연결

> 작성일: 2026-10-20 · 상위 계획: [공식모델_전환_실행계획_2026-10-20.md](공식모델_전환_실행계획_2026-10-20.md)
> 결론: 업로드 경로가 공식 OLKAVS 모델로 실제 한국어 텍스트를 낸다. 서비스 경로로 처리한 val20 결과는 2단계·step04와 20/20 같다(완료 기준 충족). 서버는 상주 워커 두 개를 띄워 모델을 한 번만 올리고, 얼굴이 계속 보이는 구간을 최대 12초 창으로 나눠 인식한다. 처음 보는 사람·웹캠 조건의 정확도는 아직 측정하지 않았다(3단계 팀 촬영 후).

## 1. 구조

```
브라우저 ─POST /api/upload─▶ FastAPI (py -3.11) ─POST /api/infer─▶ 백그라운드 Job
                                   │                                  │ FIFO 대기열(한 번에 한 영상)
                                   │            JSON 줄 규약(stdin/stdout)
                                   ├──────────▶ 입술 추출 워커 (.venv-olkavs-roi, mediapipe 0.10.21)
                                   │              영상 → tmp/roi/<session>/seg_XXX.npz (96x96 BGR)
                                   └──────────▶ 인식 워커 (.venv-olkavs, torch, multiview_lip.pt)
                                                  NPZ → 텍스트·confidence·raw_score
브라우저 ◀─GET /api/result/{session} (1초 폴링)── 시간 구간별 결과 + 품질 경고(warnings)
```

- torch와 mediapipe를 한 프로세스에 올리면 segfault가 날 수 있고 두 가상환경의 라이브러리 버전도 다르므로 프로세스를 나눴다.
- 워커는 서버가 시작할 때 백그라운드로 뜬다(GPU 기준 약 10초). 죽으면 다음 요청에서 다시 뜬다. 서버를 끄면 함께 종료된다.
- 웹캠 실시간(WebSocket v2)은 그대로 compact 경로다. compact 가중치가 없으면 "녹화 후 업로드를 쓰라"는 안내와 함께 거부한다.
- 계획서의 `recognizer.py` 공통 인터페이스와 72→69 토큰 변환은 만들지 않았다. 인식 워커가 OLKAVS 자체 사전으로 문장까지 복원해 텍스트를 돌려주므로 프로젝트 69토큰 사전을 거칠 필요가 없다.

## 2. 영상 한 개를 처리하는 방식

1. **프레임 선택**
   - 약 30fps(29.97/30) 고정 프레임률 파일만 원본 프레임을 그대로 쓴다(검증된 step04 경로).
   - 25·60·120fps, WebM, 메타데이터 이상은 실제 프레임 시각(PTS) 기준 30fps 격자로 뽑는다.
   - 30fps로 보고됐는데 읽는 도중 간격이 반 프레임 넘게 어긋나면 그 지점부터 같은 스트림을 격자 방식으로 이어 읽는다. 앞부분 결과는 버리지 않는다.
   - 같은 PTS가 반복되거나 한 프레임 이내로 살짝 뒤로 가는 프레임은 건너뛴다. 그보다 크게 뒤로 가면 손상으로 보고 "영상을 읽을 수 없습니다"로 끝낸다.
   - 27fps 미만 영상은 결과 화면에 정확도 저하 경고를 띄운다.
2. **입술 추적**
   - 검출기 하나로 영상 전체를 앞에서부터 추적한다.
   - 1~11프레임을 놓치면 직전 상자를 쓴다. 이 프레임은 보류했다가 다음 검출이 오면 발화에 넣는다. 12프레임 연속으로 놓쳐 추적을 잃으면 실패 구간으로 보낸다. 얼굴이 사라진 화면이 창 끝에 붙지 않는다.
   - 검출 프레임이 0.3초(9프레임) 미만인 짧은 run은 창을 만들지 않고 앞뒤 실패 구간과 합친다. 검출이 깜빡일 때 짧은 엉터리 창이 여러 개 생기지 않는다.
   - 0.5초 이상 이어진 실패만 `[검출 실패 구간]`으로 보고한다. 짧은 실패는 보고하지 않지만 창은 거기서 끊는다.
   - 입술 상자는 정사각형·1.5배 문맥·EMA(`stable_context_square`)로 자른다. 문맥 정사각형이 화면을 넘는 프레임도 실패 구간으로 센다.
   - 도중에 해상도가 바뀌거나 검출기가 예외를 내면 그 지점을 경계로 검출기를 새로 만든다.
3. **창 나누기**
   - 얼굴이 계속 보이는 구간을 최대 12초 창으로 나눈다.
   - 넘칠 때는 6~12초 사이에서 입 움직임이 가장 작은 지점에서 자른다. 탐색 폭은 항상 최대 길이의 절반이다.
   - 1초보다 짧게 남은 꼬리는 앞 창에 붙인다. 중간 창은 1초 미만이 되지 않는다.
4. **인식**
   - 창마다 발화 단위 정규화 → encoder → hybrid(기본) 또는 CTC 디코딩.
   - `confidence`는 프레임별 최대 확률의 기하평균(0~1), `raw_score`는 출력 문장의 CTC 로그우도다.
   - 글자가 하나도 나오지 않으면 점수 없이 `[인식 불가]`로 표시한다.
5. **대기열과 입장 제어**
   - 영상은 들어온 순서대로 하나씩 처리한다.
   - 차례가 왔을 때 남은 Job 시간(300초 − 대기 시간)이 예상 처리 시간보다 짧으면 시작하지 않는다. 대신 "잠시 후 다시 시도" 안내로 바로 끝내고 다음 작업에 워커를 넘긴다.
   - 예상 처리 시간은 `10초 + 1.25 × 영상 길이(초)`로 어림한다. 영상 길이를 메타데이터로 알 수 없으면 이 검사를 건너뛴다.

## 3. 함께 고친 것

### 기존 서비스 버그

| 문제 | 수정 |
|---|---|
| `session_id`를 검증 없이 glob에 넣어 업로드 폴더 밖 파일을 지울 수 있음 | UUID4 형식만 허용, 디렉토리 접두사 비교로 교체 |

| Job 타임아웃(300초)이 실제로 적용되지 않음 | 서버가 작업 중에 직접 판정하고 중단, 늦은 완료가 timeout을 덮지 않음 |
| 타임아웃 후 같은 세션 재요청 시 이전 작업과 경합 | 이전 작업 스레드가 끝날 때까지 409 |
| 오류 문구에 워커 로그·서버 경로가 섞여 사용자에게 노출 | 고정 문구만 전달, 상세는 서버 로그 |
| 임시 파일 정리가 서버 시작 1시간 뒤에야 실행 | 시작 즉시 1회 실행, 남은 입술 crop 폴더는 시작 시 삭제 |
| 가중치 경로 하드코딩 | `LIPNET_WEIGHTS` 환경변수, `/health`에 모델 정보 표시 |

### 2차 적대적 검토 지적

보고서 14건 중 같은 문제의 재지적 1건을 합쳐 13개 문제다. 모두 재현됐고 모두 고쳤다.

| 문제 | 수정 |
|---|---|
| 대기 시간도 Job 시간에 포함돼, 앞 작업 뒤에서 끝날 수 없는 작업이 워커를 쓰고 결국 timeout | 입장 제어로 시작 전에 안내하고 끝냄 |
| 문맥 정사각형 오류가 이어지면 그 시간이 결과 어디에도 나오지 않음 | 기하 오류 프레임을 실패 구간으로 집계 |
| 입 움직임 최소 지점 절단이 고정 10초 분할보다 경계 손실을 줄이지 못함 | 최대 12초·탐색 6초로 기본값 변경(아래 실측) |
| 검출이 깜빡이면 직전 상자 crop뿐인 0.4초 창이 쏟아지고 실패 구간은 보고되지 않음(재현 영상에서 '아' 창 11개) | 검출 0.3초 미만 run은 창 없이 실패 구간에 합침, 직전 상자 프레임은 보류 |
| 짧은 run과 짧은 실패가 번갈아 오면 실패 구간이 사라지고 영상 전체가 "프레임 없음" | 실패 조각을 하나로 합치고, 쓸 수 있는 프레임이 없으면 전체를 실패 구간으로 보고 |
| PTS가 한 번만 중복돼도 업로드 전체가 "영상을 읽을 수 없습니다" | 한 프레임 이내 중복·역행은 건너뛰고 셈, 큰 역행만 오류 |
| 영상 중간에 해상도가 바뀌면 업로드 전체 실패 | 그 지점을 경계로 검출기·기하 상태를 새로 만듦, 그 밖의 검출기 예외도 그 프레임만 실패 구간 |
| `/health`의 `last_error`에 워커 로그 꼬리·서버 경로 노출 | 짧은 상태 코드와 시각만, 요청 하나의 실패는 워커 상태로 기록하지 않음 |
| 격자 방식(30fps가 아닌 영상)에서 입술 추출 동안 진행률 0% 정지 | 영상 시간 기준 진행률, 서비스에서 감소하지 않게 보장 |
| 대기 작업 수에 이미 취소된 작업이 포함됨 | 취소된 대기 작업 제외 |
| 창 최대 길이 3~4초 설정에서 1~29프레임 창이 생김, 빈 인식 결과에 점수가 붙음 | 탐색 폭을 최대 길이 − 최소 길이로 제한, 빈 결과는 점수 없이 `[인식 불가]` |
| 가변 프레임률을 감지하면 영상을 처음부터 다시 읽음(최대 약 2배 시간) | 같은 스트림에서 격자 방식으로 이어 읽음 |
| 저프레임률 경고를 계산만 하고 버림, 25fps는 경고 대상도 아님 | 기준을 20fps에서 27fps로 올리고 결과 화면에 표시, 서버 로그는 WARNING |

### 창 길이 기본값 실측

라벨이 있는 연속 녹화 하나(C297, 302초, 28문장, 1080p 29.97fps)를 실제 서비스 경로로 두 설정에서 처리했다. 오류율은 문장부호를 뺀 전체 이어붙인 문장 기준이다.

| 설정 | 문자 오류율 | 문장 중간 절단 | 창 수 | 처리 시간 |
|---|---:|---:|---:|---:|
| 최대 10초·탐색 3초(이전) | 19.74% | 12/34 | 36 | 271.5초 |
| 최대 12초·탐색 6초(새 기본값) | 16.51% | 5/31 | 33 | 315.5초 |

- 2차 검토자의 독립 측정(19.86% → 16.01%, 14/34 → 6/32)과 방향·크기가 같다.
- hybrid 탐색 상한에 걸린 창은 없었다.
- 녹화 하나의 결과이므로 3단계 촬영 자료로 다시 확인한다.

### 자동 테스트

| 환경 | 결과 |

새 테스트가 다루는 것:
- 워커 통신: 기동·진행률·오류·시간 초과·비정상 종료·재기동·대기 시간·CUDA 손상, 실제 `serve()` 루프.
- 사용자 문구와 `/health` 상태에 경로·로그가 없음.
- FIFO 대기열, 대기 중 중단, 입장 제어, 진행률 단조성, 낮은 프레임률 경고, 빈 인식 결과.
- 프레임 선택 표(25/29.97/30/60/120/240fps, WebM, 메타데이터 이상), 격자 리샘플(동률·가변 간격·PTS 중복·역행), 도중 격자 전환.
- 가짜 검출기를 주입한 입술 추적 상태 전이: 깜빡임, 보류 프레임, 기하 오류, 검출기 예외, 짧은 실패, 해상도 변경, 시간 순서, 쓸 수 있는 프레임이 없는 영상.
- 창 나누기(서비스 기본값 12초·6초 포함), CTC 점수(전수 열거와 비교), 인식 후처리, 세션 검증, 타임아웃, 임시 폴더 정리, 결과 응답의 `warnings`.

### 완료 기준: 서비스 경로 val20 회귀

상주 인식 워커에 JSON 요청으로 val20 입력 20개를 보냈다.

| 디코더 | step04/2단계와 다른 출력 | 문자 오류율 | 완전 일치 |
|---|---:|---:|---:|
| hybrid | 0/20 | 33.58% | 5/20 |
| CTC | 0/20 | 41.38% | 0/20 |

confidence는 20개 모두 0~1 범위다.

### 실제 워커·서버로 확인한 시나리오 (RTX 3080, hybrid, 새 기본값)

| 입력 | 결과 |

| 180번 프레임 PTS 중복 | 180번에서 격자로 전환, 중복 1프레임 건너뜀, 정상 인식(수정 전 전체 오류) |
| 150번 프레임에서 960x540→640x360(AVI·MP4) | 검출기 1회 재생성, 5.0초 경계로 두 창(수정 전 전체 오류) |
| 약 16fps 가변 프레임률 | 격자로 처리, 결과 화면 위쪽에 낮은 프레임률 경고 표시(브라우저 확인) |
| 읽을 수 없는 영상 10회 반복 | 입술 추출 워커 스레드 수 그대로 |
| 실제 서버 HTTP 업로드→폴링 | 12초 영상 18.8초에 `done`, 업로드·입술 임시 파일 0개 |
| 서버 정상 종료 | 워커 프로세스 0개, 8000번 포트 해제 |

## 5. 처리 시간 (참고)

- 상주 워커 기준 GPU hybrid로 12초 영상은 창 하나로 처리되어 12.4~18.3초 걸렸다. 10초 창일 때는 약 10초였다. 정확도를 위해 지연을 늘린 선택이다.
- 긴 영상은 영상 길이의 약 1.05배였다(302초 녹화 315.5초). 이 비율이면 업로드 상한 180초 영상은 약 190초로 Job 상한 300초 안이다.
- 여러 영상이 동시에 들어오면 뒤 작업은 입장 제어로 시작 전에 안내를 받는다.
- hybrid 디코딩 시간은 출력 자모 수의 제곱에 가깝게 늘어난다. 빠른 응답이 필요하면 `LIPNET_OLKAVS_DECODER=ctc`를 쓰거나 `LIPNET_OLKAVS_SEGMENT_SECONDS`를 낮춘다.
