# 대용량 데이터와 Google Drive 사용 방식 재점검

조사일: 2026-09-24. 프로젝트 진행은 중지한 상태에서 기존 검사 기록과 공식 문서를 확인했다. 이 문서는 해결 방안이며 다운로드, 동기화 설정 변경, 원본 이동·삭제, 학습을 실행한 기록이 아니다.

## 판단

현재 문제는 두 가지다. **영상 사본이 불완전한 문제**와 **원천 데이터를 개인 PC를 거쳐 Drive에 다시 올리는 작업 방식의 비용**을 구분해야 한다. Drive의 큰 저장 용량이 다운로드용 로컬 디스크를 대체하지는 않는다. 현재 단계에는 AIHub 전체 자료를 확보하는 것보다, 필요한 화자와 문장을 정해 한 묶음씩 검증·전처리하고 로컬에서 학습하는 방식이 적절하다. 이 판단이 적은 데이터만으로 최종 인식 성능을 보장한다는 뜻은 아니다.

## 1. 무엇이 확정됐고 무엇이 아직 불명확한가

근거는 `results/step18-intake/run01/container_probe.json`, `preparation_failure.json`, `recovery_access.json`이다. 새 TS2·TS20·TS200의 정면 영상 180개를 대상으로 한 검사이며, 전체 각도 900개나 AIHub 서버 원본 전체에 대한 검사 결과가 아니다.

| 확인 항목 | 결과 | 해석 범위 |
|---|---|---|
| 선언된 MP4 박스 끝이 실제 파일 끝보다 큼 | 161개 | 파일 구조와 실제 길이가 모순됨 |
| 위 161개 파일의 실제 크기 | 모두 1MiB 정수배 | 블록 단위 중단·불완전 생성 가능성을 뒷받침하나 원인 프로그램은 특정하지 못함 |

코덱 설치, 확장자 변경, 플레이어 교체로 파일에 없는 영상 데이터를 만들 수 없다. `moov` 정보만 수선해 일부 조각을 재생할 수 있더라도 전체 문장·타임스탬프·프레임별 입술 좌표를 보장하지 못하므로 학습 원본의 복구로 취급하면 안 된다.

**다운로드 중단, 분할 파일 병합 누락, 압축 해제 실패, Drive 업로드·캐시 문제 중 어느 단계가 최초 원인인지는 아직 확정되지 않았다.** 삭제된 업로드 전 원본이 없고 해당 작업의 완료·오류 기록도 확보하지 못했기 때문이다. 1MiB 경계만으로 Google Drive나 AIHub를 원인으로 단정할 수 없다.

추가로 구분할 점이 있다. G:와 G:에서 만든 사본의 해시 비교는 DriveFS를 통한 읽기의 동일성을 확인한다. Drive 웹에서 직접 내려받은 파일과의 독립 비교는 아니다. 다만 이번 추가 점검에서 웹의 파일 크기도 18MB·8MB로 짧게 표시되었으므로, 이 두 파일에 대해 “클라우드는 온전한 큰 파일인데 G: 자리표시자만 작다”는 설명은 관측과 맞지 않는다. 더 엄밀하게 확인하려면 다음처럼 대표 파일 하나만 비교할 수 있다.

1. Drive 웹 파일 정보 확인은 완료했다. 현재 UI는 반올림된 MB 표시이므로 정확한 바이트 수 확인으로 취급하지 않는다.
2. 같은 파일을 웹에서 별도 로컬 경로로 직접 받아 크기·SHA-256·MP4 구조를 비교한다.
3. 웹 사본도 동일하게 잘렸으면 클라우드에 남은 현 버전 자체로 복구할 수 없다. 웹 사본은 온전하고 G:만 짧다면 DriveFS 경로·캐시 문제로 범위를 좁힌다.
4. AIHub에서 새로 받은 대표 원본을 업로드하기 전에 검증한다. 이것이 정상이면 종전 수신·해제·업로드 과정의 문제였다는 근거가 된다. 새 원본도 같은 위치에서 실패하면 제공처 원본 또는 새 다운로드 경로를 추가 비교한다.

현재 기록의 손상본 180개 합계는 약 13.37GiB다. 이 수치와 실패한 선정 계획의 약 1.86GB 복사 예산은 완전한 원본의 용량 예측에 사용할 수 없다. 복구본으로 인벤토리와 저장 공간 예산을 다시 계산해야 한다.

## 2. 왜 G:로 받는데 C: 공간과 추가 동기화 시간이 필요한가

Google 공식 문서에 따르면 Drive 데스크톱 앱은 Windows에서 기본적으로 `%LOCALAPPDATA%\Google\DriveFS`에 캐시를 두고, 업로드 전에 파일을 이곳에 둔다. 캐시 위치는 변경할 수 있다. 업로드가 끝나기 전에 캐시를 지우면 파일이 유실될 수 있다. 업로드와 G:에 보이는 사용 가능 공간도 캐시가 있는 로컬 파티션의 여유 공간에 제한된다. [Google Drive 관리자 FAQ](https://knowledge.workspace.google.com/admin/drive/drive-faq-for-admins)

스트리밍은 주로 클라우드에 보관하고 접근하는 파일을 로컬에 가져오는 방식이며, 미러링은 로컬과 클라우드 양쪽에 전체 사본을 둔다. 스트리밍도 작업 중인 파일의 로컬 공간을 사용한다. [Google 스트리밍·미러링 안내](https://support.google.com/drive/answer/13401938?hl=en)

이 PC의 C: 기본 DriveFS 경로에서 `content_cache` 폴더 한 개, 파일 428개, 논리 크기 합계 23,541,684,109바이트(약 21.92GiB)를 확인했다. 내용은 읽지 않았다. HKCU/HKLM의 `Software\Google\DriveFS`에서 `ContentCachePath`는 별도 설정되지 않은 상태였다. 이것은 C:에 실제 캐시 파일이 존재한다는 근거이며, 디스크 할당량·업로드 대기량·앱 내부의 모든 사용자 설정을 확인한 결과는 아니다. 공식 고급 설정은 `ContentCachePath`로 캐시 경로를 지정할 수 있다고 설명한다. [Google Drive 고급 설정](https://knowledge.workspace.google.com/admin/drive/advanced-drive-for-desktop-configuration)

사용자가 설명한 작업은 개념적으로 다음 경로다.

```text
AIHub 서버
   │ 인터넷 다운로드
   ▼
PC의 다운로드 임시 파일·DriveFS 로컬 캐시
   │ 인터넷 업로드
   ▼
Google Drive 클라우드
   │ 로컬 캐시가 없으면 다시 다운로드
   ▼
전처리·학습 프로그램
```

파일 탐색기의 G:에 쓰는 것은 AIHub 서버가 Google 서버에 직접 전송하는 명령이 아니다. 따라서 다운로드와 업로드의 두 구간이 발생한다. 캐시가 C:에 있으면 사용자가 저장 위치를 G:로 지정해도 C:를 사용한다. 큰 압축파일을 G: 안에서 해제하면 압축파일 외에 다수의 새 영상·라벨까지 동기화 대상이 되어 작업량이 늘어난다. 이후 파일을 읽을 때 캐시가 없으면 재수신 비용도 생긴다.

**사용자가 파일 묶음을 선택해 일부만 받는 행위가 잘못된 것은 아니다.** 다만 스트리밍 드라이브를 대용량 다운로드·압축 해제·학습 작업 디스크로 사용하는 구성이 현재 요구에 맞지 않는다. 캐시를 D:로 옮기면 C: 압박을 줄일 수 있지만 원천 영상 재업로드와 재수신 시간까지 없어지지는 않는다. 캐시 이동은 업로드 대기 자료와 실제 설정을 확인한 뒤 별도 작업으로 판단한다. 수동 캐시 삭제를 복구 방법으로 실행하지 않는다.

## 3. 전체 TB 데이터를 받아야 하는가

AIHub 공식 Shell은 `filekey`를 지정하면 해당 파일만 받고, 생략하면 데이터셋 전체를 받는다. 승인이 완료된 데이터셋과 API 키가 필요하다. 공식 도구는 병합·압축 해제·압축파일 제거를 수행하며, 다운로드 크기의 2~3배 이상 공간을 권장한다. 원본을 검증 전까지 보존할 이번 복구에는 자동 제거 동작을 고려해야 한다. [AIHub API/Shell 안내](https://www.aihub.or.kr/devsport/apishell/list.do)

18단계에서 웹 파일 목록으로 확인한 다운로드 단위는 다음과 같다. 사이트 표시 GB를 정확한 서버 바이트 수로 간주하지 않는다.

| 원천 묶음 | 사이트 표시 크기 | 파일 키 | 현재 정면 라벨에서 확인한 신규 화자 수 |
|---|---:|---:|---:|
| TS2.tar | 78.83 GB | 54972 | 5명 |
| TS20.tar | 86.80 GB | 54973 | 5명 |
| TS200.tar | 88.50 GB | 54974 | 5명 |

출처: [해당 AIHub 데이터 페이지](https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=538), 로컬 `recovery_access.json`, `source_index.json`. 이 세 묶음이 유일하거나 반드시 최적이라는 뜻은 아니다.

현재 자료에서 묶음 하나는 영상 300개이며 정면은 60개였다. 학습에 정면만 쓴다면 사용 파일 수는 약 1/5이나, 용량 비율까지 정확히 1/5이라고 가정할 수는 없다. **정면만 TAR에서 추출하는 것은 해제 후 저장 공간을 줄이며, 이미 선택한 TAR 파일의 인터넷 수신량을 줄이지는 않는다.** 공식 다운로드 단위가 TAR라면 TS2에서 정면만 필요해도 원천 묶음 하나는 받아야 한다. TAR의 특정 멤버만 추출하는 기능 자체는 지원된다. [GNU tar 특정 파일 추출 안내](https://www.gnu.org/software/tar/manual/html_node/extract.html)

압축파일을 중간에 끊어 10GB만 남기는 것은 적절한 부분 데이터 선정이 아니다. 원하는 용량을 내려면 완전한 공식 묶음을 선택하고, 그 안에서 완전한 파일과 문장 구간을 선정해야 한다. 분할 압축 조각도 전부 수신·정상 병합한 뒤 처리한다. 현재 공개 공식 문서에서 임의의 내부 MP4만 선택 수신하는 API는 확인하지 못했다. HTTP 범위 읽기나 비공식 미러를 전제로 계획하지 않는다.

데이터 예산은 GB보다 **화자 수, 총 발화 시간, 문장·어휘 다양성, 성별·환경·각도 구성, 화자별 분리**로 정한다. 100GB가 주로 같은 화자와 여러 각도의 반복 녹화라면 일반화에 제공하는 정보는 제한적이다. TS2·TS20의 여성/환경1과 TS200의 남성/환경6처럼 속성이 묶인 부분집합만 쓰면 성별과 환경의 효과도 섞일 수 있다. 먼저 작은 라벨 자료로 묶음별 구성을 확인하고 필요한 원천 묶음을 선택하는 편이 낫다. 이 선정은 정확도 결과를 보고 유리한 화자만 남기는 방식이 아니라 사전 기준으로 고정해야 한다.

## 4. 권장 작업 방식: 로컬에서 한 묶음씩 처리

현재 개발·학습을 로컬 GPU에서 진행할 경우의 권장안이다. 프로젝트는 멈춘 상태이며 다음 내용은 재개 전에 합의할 운영 방식이다.

```text
AIHub → D:의 동기화되지 않는 작업 폴더
      → 압축파일·대표 영상 검증
      → 필요한 정면 영상과 라벨만 추출
      → 문장별 입술 ROI·텍스트·출처 목록 생성
      → 로컬 학습
      → 검증된 결과·체크포인트·작은 캐시 묶음 백업
```

1. 다운로드와 임시 파일 위치를 Drive 밖의 D:로 지정한다. Windows 다운로드 관리자의 대상뿐 아니라 병합·해제 임시 경로도 확인한다. 기존에 준비한 `D:\lipnet_recovery\stage18\downloads`는 이 용도로 적합한 후보이며, 현재 재다운로드 완료 여부를 가정하지 않는다.
2. TS2처럼 원천 묶음 하나만 먼저 수신한다. 작업 중단은 공식 다운로드 관리자의 전송 중지·재개 기능을 이용한다. 창을 닫으면 이력이 없어질 수 있다는 AIHub 안내가 있다. [AIHub 이어받기 안내](https://aihub.or.kr/aihubnews/notice/view.do?currMenu=131&nttSn=10129&topMenu=103)
3. 파일 크기·TAR 멤버 경계·추출 읽기를 확인하고, 필요한 영상 전체 디코딩과 라벨 시간·프레임 수를 확인한다. TAR 목록 출력 성공과 파일 해시 생성만으로 영상 정상 판정을 하지 않는다.
4. 필요한 정면 파일만 별도 폴더에 추출한다. 원래 라벨, 원천 파일명·해시, 구간 시작·끝, 화자, 분리, 전처리 버전을 함께 남긴다. 입술 검출 방법을 나중에 바꿀 수 있도록 사용한 원천이나 충분한 주변 얼굴 영역을 보존할 계획도 둔다.
5. 학습 파일은 로컬 디스크에서 읽는다. 전처리 결과는 날짜·묶음·화자별로 묶어 보관하고, 모든 작은 파일을 실시간으로 Drive에 동기화하지 않는다. 캐시 묶음 크기는 예를 들어 1~4GiB 정도로 시작해 복구·재전송 시간을 측정한다. 이는 운영 제안이며 현재 코드의 확정 포맷은 아니다.
6. 사용한 원천 파일과 중요한 산출물의 두 번째 검증 사본이 확보되기 전에는 유일한 정상 원본을 지우지 않는다. 백업 성공은 업로드 표시만으로 끝내지 않고 해시 대조와 작은 실제 읽기·복구 확인을 포함한다. 외장 디스크나 국내 저장소도 가능하며 Drive가 필수는 아니다.
7. 다음 묶음으로 넘어가기 전 여유 공간을 다시 계산한다. 기존 실패 실행과 평가 분리는 보존하고, 복구한 파일의 크기·해시로 새 실행 기록을 만든다.

### 공간을 수치로 계산하는 방법

아래는 자체 산식이다. `A`는 수신한 원천 묶음, `E`는 추출한 필요한 원본, `R`은 ROI 캐시, `T`는 다운로드·병합 임시 파일, `S`는 운영 여유 공간이다.

```text
필요 여유 공간 ≈ A + E + R + T + S
```

분할 조각과 병합본이 동시에 있으면 `T`에 원천 묶음 크기만큼이 더 들어갈 수 있다. 원천 전체를 풀면 `E`도 커진다. 따라서 단순히 80GB 파일을 받는다고 80GB만 비우는 계획은 부족하다. 이번 재점검 시 C: 여유는 217,324,847,104바이트(약 202.40GiB), D:는 450,703,523,840바이트(약 419.75GiB)였다. D:는 약 80~90GB 묶음 한 개를 순차 처리하는 후보가 되지만, 실제 실행 때 여유와 임시 경로를 다시 확인해야 한다.

현재 전처리는 25fps, 96×96, RGB `uint8`를 `np.savez_compressed`에 저장한다. 압축 전 픽셀 크기는 다음과 같다.

```text
초당 25 × 96 × 96 × 3 = 691,200바이트
영상 1시간 ≈ 2.317GiB
5초 문장 1,000개 ≈ 3.22GiB
5초 문장 10,000개 ≈ 32.19GiB
```

실제 NPZ 크기는 영상의 압축률과 메타데이터에 따라 달라진다. 임의의 고정 압축률을 약속하지 않는다. `float32`를 그대로 저장하면 픽셀 공간이 네 배가 되므로 저장은 `uint8`, 학습 시 변환을 유지한다. 회색조나 동영상 압축으로 더 줄이는 것은 모델 입력·복원 오차·입술 미세 움직임에 영향을 주므로 독립 검증 뒤 결정해야 한다. 입술 영역만 남겨도 사용 시간이 수백·수천 시간이면 다시 큰 데이터가 된다.

현재 v4 학습 자료의 파일 메타데이터와 매니페스트를 집계한 실측은 **1,000문장·4,497.778초(약 74.96분), NPZ 합계 1,888,001,047바이트(약 1.76GiB)**다. 현재 구성에서는 발화 1시간당 약 1.41GiB에 해당한다. 평가 영상·NPZ의 내용을 새로 열거나 평가하지 않고 집계한 수치다. 다음 데이터도 같은 압축률이라고 보장하지 않지만, 원천 전체를 반복 업로드하는 것보다 현재 방식의 ROI 캐시를 운영하는 편이 훨씬 작아질 수 있다는 프로젝트 내부 근거다.

### 시간 낭비가 어느 정도인가

다음은 실제 회선 측정이 아닌 **십진 GB와 유효 Mbps를 사용한 예시 산식**이다. `A`는 GB, `d/u`는 실제 다운로드/업로드 Mbps다.

```text
다운로드 시간(시간) ≈ 2.222 × A / d
업로드 시간(시간)   ≈ 2.222 × A / u
순차 전송 시간     ≈ 다운로드 + 업로드
```

100GB를 유효 100Mbps로 받으면 약 2.22시간, 유효 20Mbps로 다시 올리면 약 11.11시간이다. 순차면 약 13.33시간이고, 겹쳐 진행해도 느린 구간의 시간과 동기화 대기를 피할 수 없다. 원천을 로컬에 둔 뒤 검증된 5GB 산출물만 같은 속도로 백업하면 업로드 약 33분이다. 실제 속도, 병합·해제, 파일 개수, 디스크와 캐시 대기 때문에 실측은 달라진다. 이 예에서 빨라지는 이유는 클라우드 프로그램을 바꿔서가 아니라 다시 전송하는 데이터의 양을 줄이기 때문이다.

## 5. Colab이나 서버로 옮기면 해결되는가

Colab 공식 FAQ는 VM이 유휴 상태나 최대 수명에 따라 삭제되고 GPU·자원 제공이 가변적이라고 설명한다. Drive를 마운트해 많은 작은 파일을 읽기보다, 묶음 파일을 VM으로 복사한 뒤 VM 로컬에 풀어 읽도록 권한다. Drive 저장 용량을 늘려도 Colab VM 디스크가 함께 늘어나는 것은 아니다. 따라서 Colab으로 옮기더라도 작은 검증 데이터 묶음과 체크포인트 복원 체계가 필요하다. [Google Colab 공식 FAQ](https://research.google.com/colaboratory/faq.html)

AIHub는 서버에서 Shell로 자료를 받는 기능을 공식 제공하지만, 그 사실이 모든 클라우드 지역에 데이터 반출을 허용한다는 뜻은 아니다. 현재 공개 이용정책에는 국외 이용·국외 반출의 별도 합의와 미승인 제3자 제공 제한이 명시되어 있다. **국내 지역의 저장·처리 환경을 우선 검토하고, 해외 처리 가능성이 있는 Colab이나 다른 서비스는 개별 자료의 승인 조건과 실제 지역을 확인해야 한다.** 기존 Drive 사용의 약관 위반 여부를 이 문서만으로 단정하지 않는다. ROI나 파생 데이터라고 자동 면제된다고 가정하지 않는다. [AIHub 이용정책](https://www.aihub.or.kr/intrcn/guid/usagepolicy.do?currMenu=151&topMenu=105)

서버 비용 비교에는 GPU 시간뿐 아니라 저장 GB·월, CPU 전처리 시간, 백업, 외부 전송 비용, 중단 시 재수신 비용을 포함한다. 특정 유료 서비스가 현재 로컬 장비보다 무조건 싸거나 빠르다고 결론내릴 근거는 아직 없다. 우선 작은 동일 작업의 소요 시간·최대 VRAM·처리량을 기록한 뒤 필요할 때 서버를 비교한다.

## 6. 이번 점검 후 남는 결정

현재 가장 현실적인 해결 방향은 **원본 수신·압축 해제·전처리를 Drive에서 분리하고, 로컬에서 검증한 필요한 데이터만 반복 사용하는 것**이다. 웹 크기 추가 확인은 완료했다. 다음 실제 조치는 TS2 정상 원본의 검증과 동기화되지 않는 D: 처리 공간 확정이며, 정확한 클라우드 사본 대조가 더 필요하면 대표 파일 하나만 웹에서 받아 비교할 수 있다. 프로젝트 재개 전에는 데이터 선정 단위를 GB에서 화자·발화 시간 중심으로 바꾸고, 정상 원본을 유일한 사본 상태에서 삭제하지 않는 절차를 정한다.

이번 문서에서 확인하지 않은 항목: Drive 앱 내부의 모든 사용자 설정과 업로드 대기 목록, 캐시의 디스크 할당량, 실제 네트워크 속도, 새 TS2 다운로드 완료 여부, AIHub 서버의 정확한 원천 체크섬, 구조 통과 17개의 전체 디코딩, 기존 Drive 계정의 실제 저장 지역. 확인 전까지 해당 값을 사실처럼 사용하지 않는다.
