# 프로젝트 방향·연구·대용량 데이터 운영 종합 점검

2026-09-24 · 사용자 요청에 따라 단계 진행과 새 학습은 중단하고 점검만 수행했다.

## 결론

**입술 영상에서 한국어 문장을 추출한다는 제작 방향은 맞지만, 모델을 학습시키는 전략과 데이터를 취급하는 방식은 바꿔야 한다.** 현재 코드가 목표를 달성했다는 뜻은 아니다. 기존 1~17단계는 토큰화·시간축·전처리·학습 연결과 실험 재현 기반을 마련했으나, 처음 보는 화자의 문장을 읽는 능력을 확보하지 못했다. 같은 소규모 자료와 자체 초기화 모델로 반복 실험하는 일을 계속하는 것은 우선순위가 낮다.

가장 먼저 검토할 자산은 **현재 AIHub 자료와 동일한 OLKAVS의 한국어 영상 전용 공식 모델 후보**다. 저자 공유 폴더에서 `multiview_lip.pt`(표시 290.1MB)와 `audio_visual.pt`가 실제로 보이는 것을 확인했다. 다만 파일을 다운로드·실행하지 않았으며, `multiview_lip.pt`는 다각도 All-model 후보로 보인다. 논문의 최고 V-model 성능에 대응하는 파일이라고 단정하지 않는다. [공식 코드](https://github.com/IIP-Sogang/olkavs-avspeech), [저자 공유 폴더](https://drive.google.com/drive/folders/1sElJn4efJdMRabMqk7-p6L7_3Dii5bW8)

데이터는 **G:를 작업 디스크로 쓰는 방식에서 벗어나, D:의 동기화되지 않는 폴더에서 한 묶음씩 처리하고 필요한 산출물만 백업**하는 편이 맞다. 먼저 20TB를 모두 확보할 필요는 없다. 작은 데이터만으로 최종 성능이 보장된다는 의미가 아니라, 사전학습 모델의 도입 가능성과 필요한 데이터 구성을 확인한 뒤 확대하자는 순서 변경이다.

## 1. 최종목표와 현재 상태

최종목표는 웹캠에 보이는 상대방의 입술 움직임만으로 한국어 발화 내용을 텍스트로 추정하는 프로그램이다. 소리를 입력받는 ASR이나 소리와 영상을 함께 쓰는 AVSR의 성능으로 이 목표 달성을 주장할 수 없다. 학습 과정에서 음성을 보조 신호로 쓰더라도 최종 추론 입력은 영상만으로 평가해야 한다.

| 점검 항목 | 현재 확인 | 판단과 해결 방향 |
|---|---|---|
| 입력과 출력 | 웹캠 `audio:false`, 입술 RGB ROI→한국어 자소→문자열 | 최종목표와 맞는다 |
| 자체 모델 | 약 329만 변수, 3D CNN→양방향 LSTM→CTC 69클래스 | 유효한 교육·실험 기준선이다. 시각 사전학습 모델과 비교할 필요가 있다 |
| 사전학습 | 자체 소수 문장 학습에서 시작. ImageNet 평균·표준편차만 사용 | ImageNet 정규화는 사전학습이 아니다. 외부 대규모 사전학습 표현 없이 소규모 자체 자료에서 학습한 표현에 의존한다 |
| 자료 규모 | v4 train 8명·1,000문장·약 75분 | 연결·암기 검사에는 유용하지만 새로운 화자·웹캠 조건의 일반화 근거로 부족하다 |
| 최근 실험 | 17단계 B: 미학습 60문장 자모 CER 79.44%, 다른 화자 개발 20문장 78.03%, 합계 완전 일치 0/80 | 해당 비교에서 인식 성능은 부족하다. 이전 단계의 다른 디코더 점수와 단순 순위 비교하지 않는다 |
| 동작 정보 활용 | 정상·정지·순서 섞기 대조에서 정상 순서의 이점이 일관되지 않음 | 입술 시간 변화를 읽는 능력이 확인되지 않았다. 영상을 전혀 쓰지 않는다고 단정할 수도 없다 |
| 전처리 | 학습은 AIHub bbox, 웹캠은 MediaPipe 검출; 학습 증강 없음 | 같은 영상에 두 경로를 적용해 crop 위치·크기·정렬 차이를 먼저 측정해야 한다 |
| 실시간성 | BiLSTM, 청크마다 누적 발화 재추론, CPU 서비스 경로 | 실시간 전송 UI는 있으나 지연이 제한된 streaming 인식기는 아니다 |
| 실제 서비스 가중치 | 설정된 `backend/models/weights/baseline_jamo_v2.pt` 없음 | 웹캠은 `MODEL_NOT_READY` 경로다. 실험 성공과 서비스 배포를 구분해야 한다 |

근거: [코드 정합성 감사](코드_정합성_감사.md), [17단계 기록](../단계별_개선/17_학습량과_자료확대_비교.md). 최종 test50은 이번 점검에서 추론하지 않았다.

유지할 것은 한글 정규화·자소 처리, 실제 프레임 시각 사용, CTC 길이 검사, 화자·발화 분리, 해시와 실행 기록, 잘못된 입력을 거부하는 처리, 웹캠 전송 기반이다. 우선 멈출 것은 같은 자료를 더 오래 반복하는 실험, 구조 이름만 바꾸는 비교, 가중치·독립 평가 없이 실시간 성능을 목표치로 확정하는 일이다.

## 2. 논문과 유사 프로젝트에서 확인한 내용

논문 원문과 저자 코드·모델·라이선스를 대조했다. 주요 8개와 최근 추가 연구를 검토했으며, 모든 논문을 망라한 순위표는 아니다. 데이터셋, 언어, 화자 분리, CER 단위, 디코더, 입력 모달리티가 달라 서로의 점수를 직접 비교하지 않았다.

| 연구·공개 구현 | 핵심 내용 | 반영할 점과 한계 |
|---|---|---|
| [LipNet](https://arxiv.org/html/1611.01599) | 시공간 CNN+BiGRU+CTC로 영어 문장 인식 | 현재 구조 계열의 타당한 출발점. 제한된 GRID 문법의 성능을 자유 한국어 대화 성능으로 해석하면 안 된다 |
| [AV-HuBERT](https://arxiv.org/html/2201.02184) | 많은 오디오·영상에서 표현을 사전학습한 뒤 영상 전용 인식으로 전이 | 처음부터 학습하는 부담을 줄이는 근거. 한국어 출력기, 입력 전처리, 연구용 라이선스 조건을 확인해야 한다 |
| [Auto-AVSR](https://github.com/mpc001/auto_avsr) | 자동전사로 자료를 늘리고 사전학습 시각 특징·Conformer 등을 사용 | 시각 특징 전이, 증강, 새 자료 적응 절차를 참고. 영어 모델을 그대로 한글 모델로 쓰지는 못한다 |
| [MuAViC](https://github.com/facebookresearch/muavic) | 약 1,200시간, 9개 언어 AVSR·번역 자료와 모델 | 한국어가 없어 즉시 대체재가 아니다. 다국어와 한국어 지원을 구분한다 |
| [OLKAVS](https://arxiv.org/html/2301.06375) | 현재 AIHub와 동일한 한국어 자료, V/AV 및 촬영 각도별 기준선 | 가장 직접적인 비교 대상. 자소·문장별 입 ROI 방향은 부합하며, 해당 공식 가중치에 맞는 frontend·전처리 재현이 우선이다 |
| [KMSAV](https://github.com/etri/kmsav) | 자연스러운 한국어 다자 대화 자료와 AVSR 전이 | 스튜디오 밖 환경 차이를 평가하는 참고 자료. 대표 A/AV 결과를 입술 전용 성능으로 쓰면 안 된다 |
| [MultiVSR 2025](https://www.robots.ox.ac.uk/~vgg/research/multivsr/) | 약 12,000시간·13언어, 사전학습 시각 특징과 언어 식별 | 전처리·화자 분리 참고. 한국어가 없고 개인 PC에서 전체 학습 재현은 우선순위가 낮다 |
| [Streaming AVSR 연구](https://www.isca-archive.org/interspeech_2023/ma23_interspeech.pdf) | 미래 문맥을 제한한 chunk 모델과 지연·오류율 절충 | 문장 종료 후 출력과 지속적인 확정 자막 출력을 별도 과제로 다룬다 |

OLKAVS 원문은 오디오 1,150시간과 여러 시점 영상 5,750시간을 구분한다. 영상 시간 전체가 서로 다른 문장 5,750시간을 뜻하지 않는다. V-only CER 26.64%와 AV CER 3.64%도 별개의 결과다. 공개 `multiview_lip.pt`의 결과를 26.64%라고 약속할 수 없으며, 우리 자모 CER·소수 검증셋과도 직접 비교할 수 없다. V-model은 외부 시각 사전학습을 쓰지만 All-model은 처음부터 학습한 모델이므로, 정확한 가중치에 맞는 구조를 확인해야 한다. [OLKAVS 원문](https://arxiv.org/html/2301.06375)

자세한 입력 해상도·언어·라이선스·학습 규모와 2025~2026 검색 범위는 [연구 근거](연구_근거.md)에 정리했다. 예를 들어 최신 Zero-AVSR에는 한국어 자료가 포함되지만, 오디오+영상 결과를 한국어 영상 전용 완성품의 증거로 쓰지는 않았다.

## 3. 수정할 제작 전략

**우선안은 한국어 공식 모델 후보의 재현 검증이고, 대안은 사전학습 시각 인코더를 한국어에 적응하는 것이다.** 이번에 구현하거나 모델을 교체한 것은 아니며, 재개 후 검증 순서다.

1. **공식 한국어 후보 확인:** OLKAVS 영상 전용 가중치와 정확한 config·토큰 사전·frontend·입력 조건·사용 조건을 맞춘다. 현재 69클래스 모델의 가중치 경로에 다른 checkpoint를 복사하는 방식으로 교체하지 않는다.
2. **짧은 정상 영상으로 작동 검증:** 별도 환경에서 공식 추론을 재현하고 RGB/회색조, FPS, crop, 정렬, 정규화, 사전 순서가 맞는지 확인한다. 해당 파일이 V-only로 작동하는지도 검사한다. 290MB 가중치 크기는 VRAM 사용량이나 실행 성공을 보장하지 않는다.
3. **독립 평가 설계:** 공식 모델이 AIHub Training 전체를 봤다면 프로젝트 내부에서 떼어 둔 TS 화자도 학습한 화자일 수 있다. 기존 heldout을 그대로 독립 평가라 부르지 않는다. 공식 분할과 모델 학습 출처를 확인하고, 동의를 받아 새로 촬영한 웹캠 평가를 별도로 고정한다.
4. **웹캠 전처리 맞추기:** 같은 원본을 bbox와 실제 서비스 검출 경로로 각각 가공해 비교한다. 얼굴 정렬, crop 흔들림, 검출 실패, FPS 누락을 확인한다. 사전학습 모델의 전처리가 RGB96 계약과 다르면 별도 버전으로 관리한다.
5. **첫 시연 범위 명확화:** 정면의 한 사람이 한 문장을 말하고 종료한 뒤 텍스트를 출력하는 조건으로 먼저 평가한다. 이는 자유 문장 목표를 제한 문장 분류기로 바꾸는 것이 아니다. 숫자·영문 처리 범위와 인식 불가 표시도 명시한다.
6. **필요한 한국어 자료만 확대:** 실패 유형을 보고 화자·문장·환경을 다양하게 선정한다. 도입이 불가능하거나 성능이 부족하면 Auto-AVSR 등의 시각 frontend 전이를 비교한다. 새로운 자료를 확보할 때 train/dev/test를 먼저 고정한다.
7. **정확도와 지연을 나눠 개선:** 문장 CER·전체 CER·WER·완전 일치·무발화 오출력을 측정하고, 발화 종료 대기·전처리·모델 시간·화면 표시 시간을 따로 기록한다. 현재 종료 대기만 약 480ms이므로 총 400ms를 달성했다고 할 수 없다.

영상에는 구분되지 않는 발음이 있어 문맥이 필요하지만, 언어 모델이 자연스러운 문장을 만든다고 입술에서 그 말을 읽었다는 뜻은 아니다. LM을 도입한다면 적용 전·후 오류와 무발화 오출력을 별도로 검증해야 한다. 학습용 증강은 crop·밝기·정렬·시간 가림 등의 검증된 방법을 검토하되, 사전학습 입력 조건을 먼저 맞춘다.

현재 GPU는 **RTX 3080, VRAM 10GB**다. 지금의 경량 모델 실험은 가능했지만, 수백만·수억 변수 사전학습 모델의 전체 미세조정이 모두 가능하다고 보장할 수 없다. 추론→인코더 고정→일부 층 적응 순서로 최대 메모리와 속도를 실측한 뒤 필요할 때 서버를 검토한다. 새로 거대한 사전학습을 수행할 계획은 우선하지 않는다.

## 4. Drive 영상은 무엇이 잘못됐나

기존 180개 정면 영상 검사 결과는 **161개 MP4 박스 길이 초과, 2개 0바이트, 17개 구조 검사만 통과**다. 161개의 파일 크기는 모두 1MiB 정수배다. 이는 블록 단위로 생성·전송이 중단됐을 가능성을 뒷받침하지만 어떤 프로그램이 원인인지는 특정하지 못한다.

이번에는 Drive 웹 파일 정보도 추가 확인했다.

| 파일 | 기존 G: 실제 크기 | Drive 웹 표시 | 의미 |
|---|---:|---:|---|
| `lip_J_1_F_02_C040_A_001.mp4` | 18MiB | 크기·사용량 18MB | 웹에 저장된 크기도 작음. 이 파일은 내부 mdat 선언 끝이 약 349MB라서 구조가 맞지 않음 |
| `lip_J_1_F_02_C040_A_002.mp4` | 8MiB | 크기·사용량 8MB | 두 번째 파일도 웹과 G:가 같은 작은 크기 규모를 보임 |

웹 UI는 반올림 표시이며 별도로 웹 사본의 전체 SHA를 계산한 것은 아니다. 그래도 ‘클라우드에는 정상 크기의 영상이 있고 G:만 덜 내려왔다’는 설명은 이 두 파일의 관측과 맞지 않는다. 첫 파일에는 이전 버전도 보이지 않았다. **동기화를 더 기다리거나 플레이어·코덱만 바꾸는 것으로 해결할 문제로 보기 어렵다.**

처음 잘못된 지점은 미확정이다. 원본 압축파일·업로드 전 사본이 삭제됐으므로 다음 가설을 구별할 기록이 부족하다.

| 가능한 원인 | 확인하려면 필요한 근거 |
|---|---|
| 원천 다운로드·분할 병합이 불완전 | 정상 완료 기록, 원본 크기·공급자 checksum, 모든 조각과 TAR 읽기 결과 |
| 압축 해제 중 공간 부족·쓰기 실패 | 해제 오류 기록과 업로드 전 추출본의 크기·디코딩 결과 |
| Drive 쓰기·캐시·업로드 과정의 중단 | 당시 동기화 오류·남은 업로드·완전한 업로드 전 사본 |
| 잘못된 MP4 길이 헤더 | 완전한 원천과 바이트 비교. 다수의 MiB 경계·0바이트까지 이를 원인으로 설명할 근거는 현재 없음 |

따라서 원인 프로그램을 확정했다고 말하지 않는다. 복구는 완전한 원본 또는 실제 이전 버전이 필요하다. 짧은 조각을 수선해 재생되게 해도 원래 문장·프레임 라벨 정렬을 복구했다는 의미는 아니다. [기존 상세 검사](../단계별_개선/18_신규자료_무결성점검_및_복구.md), [이번 실측 기록](실측_근거.json)

## 5. G:에 받는데 왜 C: 공간과 시간이 드나

Google 공식 설명상 스트리밍 Drive는 업로드 전에 로컬 캐시를 사용하며, Windows 기본 위치는 `%LOCALAPPDATA%\Google\DriveFS`다. 이번 PC에서도 그 아래 캐시 428개 파일의 논리 크기 합계 **23,541,684,109바이트(약 21.92GiB)**를 확인했다. 실제 할당 디스크 공간이나 업로드 대기량을 측정한 것은 아니다. [Google 공식 캐시 FAQ](https://knowledge.workspace.google.com/admin/drive/drive-faq-for-admins)

```text
현재 방식
AIHub → PC 임시 파일/Drive 캐시 → Google Drive 업로드
                                  ↓ 캐시가 없을 때 다시 수신
                              전처리·학습

권장 방식
AIHub → D: 작업 폴더 → 검증 → 필요한 원본/입술 캐시 → 로컬 학습
                                           └→ 선정한 산출물만 백업
```

**100~200GB 정도의 완전한 묶음만 선택해 받는 것은 잘못이 아니다.** 문제는 G:를 원천 다운로드·압축 해제·학습 작업 공간으로 쓰면서 로컬 공간과 전송 비용이 사라질 것이라고 기대하는 데 있다. G: 다운로드는 AIHub 서버에서 Google 서버로 직접 복사하는 동작이 아니다. 큰 TAR와 해제한 영상까지 모두 동기화하면 업로드량도 늘어난다.

예를 들어 100GB를 실효 100Mbps로 받는 데 약 2.22시간, 실효 20Mbps로 다시 올리는 데 약 11.11시간이 걸린다. 순차 처리 가정이면 전송만 약 13.33시간이며, 실제로는 일부 겹칠 수 있다. 회선 속도를 실측한 수치가 아닌 산식 예다. 원본 업로드를 없애고 검증 산출물 5GB만 같은 속도로 백업하면 업로드는 약 33분으로 줄어든다.

캐시를 D:로 옮기면 C: 부담은 줄 수 있지만 업로드 시간까지 없어지지는 않는다. **현재 캐시를 수동으로 지우지 않는다.** Google은 업로드 전 캐시 삭제 시 파일 유실 가능성을 명시한다. 이번에는 캐시와 설정을 변경하지 않았다. [Google 캐시 위치 설정](https://knowledge.workspace.google.com/admin/drive/advanced-drive-for-desktop-configuration)

## 6. TB 데이터의 현실적인 운영안

1. **모델·평가 목적을 먼저 정한다.** 지금은 공식 한국어 후보 검증이 우선이며 TS20·TS200까지 연속 다운로드를 진행하는 단계가 아니다. 추가 자료는 GB가 아닌 화자 수·발화 시간·문장·각도·환경 다양성으로 선정한다.
2. **완전한 TAR 한 개씩 D:에 수신한다.** 현재 여유는 약 419.75GiB다. `D:\lipnet_recovery\stage18\downloads`와 `verified`는 이미 마련돼 있다. 다운로드뿐 아니라 병합·해제 임시 위치도 확인한다.
3. **압축파일과 영상까지 확인한다.** TAR 목록이 열린다는 것만으로 충분하지 않다. 필요한 멤버의 읽기·전체 영상 디코딩·라벨 시간·프레임 수·좌표를 검사한다.
4. **필요한 영상만 추출하고 필요한 문장만 가공한다.** 해당 묶음은 300영상 중 정면 60개였지만 바이트가 정확히 1/5이라는 뜻은 아니다. TAR 내부 선택 추출은 해제 공간을 줄이며, 공식 다운로드 단위인 TAR의 수신량은 줄이지 않는다. 내부 MP4만 원격 수신하는 기능을 확인한 것은 아니다.
5. **로컬 가공본으로 반복 학습한다.** 현재 train 1,000문장·약 75분 NPZ는 **1,888,001,047바이트(약 1.76GiB)**다. 현재 RGB96·25fps·uint8의 픽셀 배열 용량은 메타데이터를 제외하고 시간당 약 2.317GiB이며, 실제 압축률은 달라진다. 20TB 원본을 매 epoch 내려받을 필요가 없다.
6. **보존과 백업을 별도 단계로 둔다.** 사용한 원천 영상·라벨·전처리 버전·해시를 남긴다. 재전처리를 위해 원본이나 충분한 얼굴 영역을 보존해야 하므로 입술 crop만 유일한 사본으로 남기지 않는다. 정상 원본의 두 번째 검증 사본 없이 마지막 원본을 삭제하지 않는다.

공간 예산은 `압축본 A + 필요한 추출본 E + 가공본 R + 병합/임시 T + 여유 S`로 계산한다. 분할 조각과 병합본이 동시에 있으면 T가 A만큼 더 필요할 수 있다. AIHub Shell은 파일 키 선택 다운로드와 자동 병합·해제를 제공하며 2~3배 여유 공간을 안내한다. 자동 원본 제거 동작도 있어 복구 과정에서는 보존 정책을 먼저 확인해야 한다. [AIHub 공식 안내](https://www.aihub.or.kr/devsport/apishell/list.do)

클라우드가 꼭 필요하면 국내 학교·연구실 서버나 국내 처리 지역의 서버가 원천을 직접 받아 전처리·학습하는 방안을 비교한다. Colab은 GPU·VM 수명과 공간이 가변적이고, Drive의 작은 파일을 반복 읽는 문제도 그대로 생길 수 있다. 공식 FAQ도 묶음을 VM 로컬에 풀어 읽는 방식을 권한다. AIHub의 국외 반출 관련 조건과 실제 처리 지역도 먼저 확인해야 하므로 무조건적인 Colab 이전은 해결책이 아니다. [Colab FAQ](https://research.google.com/colaboratory/faq.html), [AIHub 이용정책](https://www.aihub.or.kr/intrcn/guid/usagepolicy.do?currMenu=151&topMenu=105)

## 7. 이번에 처리한 것과 재개 조건

완료한 것은 코드·실험·문서 대조, 주요 연구 원문과 공개 구현 조사, 공개 한국어 가중치의 파일 존재 확인, Drive 웹 크기와 로컬 캐시·데이터 크기 확인, 손상과 전송 구조를 구분한 진단, 문서의 현황·목표·입력 길이 설명 정리다. 코드·가중치·원본 데이터·Drive 설정은 바꾸지 않았고, 새 모델 실행·학습·대용량 다운로드는 하지 않았다.

해결되지 않은 것은 손상 영상 원본 재확보, 최초 손상 발생 단계 특정, 공식 모델 실행 재현, 새로운 화자·웹캠 성능과 지연이다. 이를 해결했다고 간주하지 않는다.

재개 시에는 **공식 한국어 영상 전용 모델 도입 검증 → 독립 웹캠 평가 계획 → 필요한 자료 선정 → D:에서 검증·가공 → 비교 실험 → 서비스 연결** 순서로 진행하는 것을 제안한다. 18단계 다음 번호를 자동 진행하지 않는다.
