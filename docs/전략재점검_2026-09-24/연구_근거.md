# 한국어 웹캠 립리딩 프로젝트: 연구 근거와 도입 판단

조사일: 2026-09-24. 이번 작업은 설계 재검토이다. 모델 학습, 모델 다운로드, 의존성 설치, 데이터셋 다운로드는 실행하지 않았다.

최종목표는 **마이크의 음성을 인식하는 것이 아니라, 웹캠으로 보이는 상대방의 입술 움직임만으로 한국어 문장을 출력하는 것**이다. 따라서 논문의 VSR/visual-only 결과가 직접 관련된다. ASR/audio-only, AVSR/audio+video의 좋은 결과를 입술만 사용하는 성능으로 해석해서는 안 된다.

## 판단

현재의 `입술 영상 → 시공간 특징 → 시퀀스 모델 → 한국어 자소 → 텍스트` 방향은 최종목표에 맞는다. 그러나 소수 화자의 약 75분 자료로 작은 모델을 처음부터 학습하고, 소규모 검증셋을 반복 확인하는 전략만으로 일반인 웹캠 한국어 문장 인식에 도달할 근거는 부족하다. 이는 모델 이름이나 CTC를 바꾼다고 해결되는 종류의 차이가 아니다. **사전학습 지식을 이용하는 기준선, 충분히 다양한 한국어 자료, 웹캠 환경에서의 독립 평가**가 필요하다는 것이 아래 연구에서 얻은 설계 판단이다.

가장 직접적인 발견은 **현재 AIHub의 ‘립리딩(입모양) 음성인식 데이터’가 OLKAVS라는 공개 연구의 데이터이며, 저자들이 한국어 립리딩 코드와 기준선 모델 제공 링크를 공개했다는 사실**이다. 즉, 작은 LipNet 계열 모델만 계속 조정하기 전에 동일 데이터의 공식 한국어 기준선을 먼저 검토할 이유가 있다. 공개 폴더의 `multiview_lip.pt`(화면 표시 290.1MB)와 `audio_visual.pt` 파일 존재도 확인했다. 다만 가중치 다운로드·실행은 하지 않았으므로 실행 성공이나 현재 PC에서의 정확도를 확인한 것은 아니다. [OLKAVS 공식 저장소](https://github.com/IIP-Sogang/olkavs-avspeech), [저자 공개 폴더](https://drive.google.com/drive/folders/1sElJn4efJdMRabMqk7-p6L7_3Dii5bW8)

### 1. LipNet: 현재 모델과 닮은 이유, 참고할 때의 한계

원문은 3단 시공간 CNN에서 특징을 얻고 2단 Bi-GRU와 CTC로 가변 길이 문자를 출력한다. 전처리는 25fps, 얼굴 랜드마크·정렬, 입 중심 100×50 RGB crop이다. 현재 모델의 Bi-LSTM은 원문의 GRU와 다른 구현이지만 전체 원리는 같은 계열이다. CTC는 프레임별 정답 없이 문장 전사를 학습할 수 있어 현재 목적에 맞는 선택이다.

그러나 GRID는 자유 대화가 아니라 단어 종류와 순서가 제한된 6단어 문장이다. 논문 역시 화자 중복 평가와 처음 보는 화자 평가를 구분한다. 양방향 RNN은 입력 문장 뒤쪽 프레임도 이용하므로 그대로는 확정 출력을 즉시 내는 인과적 streaming 모델이 아니다. 모델을 유지하더라도 교육용 기준선·회귀 검사 역할로 두는 편이 타당하다. [LipNet 원문, §3–4](https://arxiv.org/html/1611.01599), [저자 코드·라이선스](https://github.com/bshillingford/LipNet)

### 2. AV-HuBERT: 오디오로 배운 지식이 영상 전용 모델에도 쓰일 수 있음

사전학습은 오디오와 영상을 이용하지만, 미세조정·추론에서 `video`만 사용하는 립리딩 경로를 제공한다. 음성이 있는 AIHub 자료를 학습 과정에 활용한다고 최종 프로그램이 반드시 마이크를 요구하는 것은 아니다. 같은 구조에서 사전학습 유무를 바꾼 논문 실험은 사전학습의 이점을 직접 검증한다.

기본 입력은 25fps, 정렬한 96×96 입 ROI, grayscale, 학습 시 88×88 random crop/평가 시 center crop이다. 현재 RGB96 캐시를 변환 없이 꽂으면 사전학습 조건과 다르다. 공식 코드는 Python 3.8·fairseq 계열이며 2024년 보관 처리되었다. 연구용 라이선스는 비상업 연구로 범위를 제한하고 production 용도를 제한하므로, 코드 공개를 곧 제품 배포 허가로 해석하지 않는다. 한국어 디코더를 새로 학습해야 하며, 영어 디코더를 단순히 자소 69개 출력층으로 바꾸는 것만으로 한국어 능력이 생기지는 않는다. [원문, §4·부록 B](https://arxiv.org/html/2201.02184), [공식 코드](https://github.com/facebookresearch/av_hubert), [공식 라이선스](https://raw.githubusercontent.com/facebookresearch/av_hubert/main/LICENSE)

### 3. Auto-AVSR: 현재 프로젝트에 적용할 것은 전이 경로와 전처리 일치

핵심은 거대한 모델 이름보다 신뢰할 수 있는 학습 쌍을 대량 확보하고 사전학습 front-end를 사용하는 과정이다. 오디오로 자동 전사한 정답을 이용해 **영상 전용** 인식기도 학습한다. 입 ROI, 정규화, random crop/flip/time masking, 길이별 batching을 사용하며 영어 SentencePiece를 사용한다. 한국어에는 토크나이저와 출력 사전을 별도로 맞춰야 한다. [Auto-AVSR 원문, §2–3](https://arxiv.org/html/2303.14307)

공식 저장소에는 `transfer-frontend`, `transfer-encoder`와 새 데이터셋 학습 안내가 있다. 2025년 의존성 간소화가 반영되었고 현재 코드 라이선스는 Apache-2.0이다. 반면 같은 저자의 오래된 `Visual_Speech_Recognition_for_Multiple_Languages`는 연구·비교 용도 제한을 명시한다. 저장소와 가중치의 출처를 정확히 구분해야 한다. 기존 영어 모델의 시각 표현을 이용하는 경로를 권장 후보로 두되, 한국어 출력과 공개 가중치 조건은 별도 검증한다. [현재 코드](https://github.com/mpc001/auto_avsr), [새 데이터 안내](https://raw.githubusercontent.com/mpc001/auto_avsr/main/INSTRUCTION.md), [현재 라이선스](https://raw.githubusercontent.com/mpc001/auto_avsr/main/LICENSE), [다른 저장소의 제한](https://raw.githubusercontent.com/mpc001/Visual_Speech_Recognition_for_Multiple_Languages/master/LICENSE)

### 4. MuAViC: ‘다국어’와 ‘한국어 지원’은 별도 사실

9개 언어에 대해 전사·번역과 평가 분할을 제공하고 AV-HuBERT에서 출발한다. 추론 모달리티 선택에 video도 있지만, 대표 AVSR/번역 결과는 입력 조건을 확인해야 한다. 한국어는 언어 목록에 없다. 이 프로젝트에선 다운로드 대체재보다 다국어 전이 및 평가 설계의 참고 자료이다. 라이선스는 CC-BY-NC 4.0이고 기반 AV-HuBERT의 조건도 따로 존재한다. [MuAViC 원문, 표1](https://arxiv.org/html/2303.00628), [공식 코드·모델·모달리티 안내](https://github.com/facebookresearch/muavic)

### 5. OLKAVS: 가장 먼저 확인해야 할 동일 데이터의 한국어 기준선

공식 저장소는 현재 AIHub 자료로 직접 연결된다. 논문은 화자를 train/validation/evaluation 8:1:1로 분리하며 공개는 train과 validation이라고 설명한다. 한국어를 초성 19·중성 21·종성 27 자소로 표현하고 문장 시간과 입 bounding box로 자른다. 현재 프로젝트의 자소·문장별 입 ROI 방향은 이와 부합한다.

V-model은 영어 자료로 사전학습한 시각 front-end를 고정한 Conformer/Transformer 계열이다. 공식 전체 validation에서 V-only CER 26.64%, WER 47.89%를 보고하지만, AV-model의 CER 3.64%는 소리도 사용한 결과다. 이 수치를 현재의 작은 검증셋 결과와 직접 순위 비교할 수 없다. 다각도 실험에서는 정면만 학습한 모델보다 여러 각도를 학습한 모델이 유리했다. 처음부터 모든 카메라를 확보할 필요는 없으나, 나중에는 실제 웹캠 자세 변화에 대응할 근거가 된다. [OLKAVS 원문, §2.3·3](https://arxiv.org/html/2301.06375)

공식 코드는 문장별 96×96 crop과 선택적인 사전학습 특징 추출을 제공한다. `v_inference.yaml`에는 `architecture: video`, 자소 토큰화, hybrid CTC/attention과 RGB 입력 설정이 있다. **따라서 현 69-class CTC checkpoint와 공식 checkpoint는 서로 바꿔 넣을 수 없다.** 시각 front-end, 출력 사전 순서, 색상·fps·정규화, decoder와 가중치 형식을 함께 맞춰야 한다. 스크립트 MIT라는 설명과 별개로 데이터·가중치·외부 사전학습 front-end의 조건은 함께 확인해야 한다. [공식 저장소](https://github.com/IIP-Sogang/olkavs-avspeech), [영상 전용 추론 설정](https://github.com/IIP-Sogang/olkavs-avspeech/blob/main/configs/v_inference.yaml)

공유 폴더의 `multiview_lip.pt`는 이름과 README의 링크 위치상 All-model 후보로 보인다. **위의 V-model CER 26.64%에 대응하는 가중치라고 단정할 수 없다.** README는 AV-model과 All-model 행에 공유 링크를 두고 V-model 행에는 별도 링크를 두지 않았다. 이 파일의 정확한 대응 모델·학습 범위·출력 사전은 나중에 config와 state를 확인해야 한다. 이번 read-only 웹 확인으로 확정한 것은 파일명과 화면 표시 크기뿐이다. [저자 가중치 공유 폴더](https://drive.google.com/drive/folders/1sElJn4efJdMRabMqk7-p6L7_3Dii5bW8)

### 6. KMSAV: 한국어 자연 대화 적응의 참고 근거

KMSAV는 YouTube 기반 다자 자연 대화라서 자세 변화, 겹친 발화, 입 가림을 포함한다. 논문의 원본 영상 약 147.9시간과 문장 구간 84.4시간, 현재 README의 83시간 표시는 동일 종류의 양으로 합산하면 안 된다. 논문은 영어로 사전학습한 AV-HuBERT를 한국어 77.5시간에 미세조정하고 초기에는 encoder를 동결한다. 다만 보고한 모달리티는 A와 AV이며 그 CER를 입술 전용 결과로 인용할 수 없다. [KMSAV 원문, 표3·§4](https://onlinelibrary.wiley.com/doi/10.4218/etrij.2023-0352)

공개 저장소는 원본 전체 영상 대신 URL과 발화·화자 얼굴 메타데이터, 준비 코드를 제공한다. 다시 원본을 수집·자르는 비용과 삭제된 URL 문제가 있을 수 있어 당장 AIHub 손상의 단순 대체재로 삼지 않는다. 향후 스튜디오 밖 평가 후보이며, 영상 수준 분할이므로 별도 화자 중복 확인도 필요하다. 코드 MIT와 데이터의 CC BY-NC-SA 4.0을 구분한다. [공식 저장소](https://github.com/etri/kmsav), [준비 절차](https://raw.githubusercontent.com/etri/kmsav/main/HOWTO.md)

### 7. MultiVSR 2025: 최신 다국어 연구도 데이터·시각 표현을 중요하게 봄

이 연구는 약 12,000시간의 13개 언어 영상과 사전학습 VTP 특징을 사용한다. 얼굴 추적, 25fps 변환, SyncNet 동기 검사, 자동 전사, 화자 분리 후 Transformer가 언어와 문장을 함께 출력한다. 목록에는 일본어·중국어는 있지만 한국어가 없다. Whisper 토크나이저가 한국어 문자를 표현할 수 있다는 것과 한국어 입술을 학습했다는 것은 별개다. [저자 논문, §III–IV](https://www.robots.ox.ac.uk/~vgg/publications/2025/Prajwal25/prajwal25.pdf)

2025년 6월 가중치·영상 추론 코드, 8월 전처리 코드를 공개했다. 공개 예시는 영상 파일을 처리하는 방식이며 한국어 streaming 지원 근거는 아니다. 루트와 README에서 명확한 라이선스 선언을 확인하지 못했으므로 재사용 권한을 임의로 단정하지 않는다. 지금 단계에서는 모델 전체 재현보다 전처리·화자 분리·입력과 출력 언어의 분리 개념을 반영할 가치가 있다. [공식 프로젝트](https://www.robots.ox.ac.uk/~vgg/research/multivsr/), [코드·가중치 안내](https://github.com/Sindhu-Hegde/multivsr)

### 8. Streaming 연구: 실시간 UI와 인식 지연은 다름

Interspeech 2023 연구는 미래 프레임을 제한하는 chunk 단위 encoder/decoder를 만들고 알고리즘 지연을 약 1.06초로 명시한다. 동일 연구의 영어 V-only 비교에서 non-streaming WER 38.6%, streaming 50.6%를 보고한다. 미래 문맥을 줄이는 것은 영상만으로 구별하기 어려운 발음을 판별하는 데 손해가 될 수 있다는 직접적인 근거이다. [원문, §4–5·표1](https://www.isca-archive.org/interspeech_2023/ma23_interspeech.pdf)

별도의 PyTorch 공개 구현은 Emformer RNN-T로 웹캠·마이크 streaming을 구현하고 BSD-2-Clause 코드 공개를 안내한다. 그러나 이것은 위 논문의 chunk Conformer와 동일 모델이 아니며, 영어 AVSR 성능을 한국어 VSR 성능으로 바꿔 읽을 수 없다. 참고할 요소는 timestamp, capture/preprocess/inference 분리, bounded buffer, 지연과 RTF 측정이다. 초기 제품 범위를 ‘버튼으로 문장 녹화 → 종료 후 결과’로 두는 것은 최종목표에 맞는 중간 목표이고, streaming은 별도 검증 과제이다. [PyTorch 공식 구현 설명](https://pytorch.org/blog/real-time-speech-rec/), [장치 입력 공식 튜토리얼](https://docs.pytorch.org/audio/2.5.0/tutorials/device_avsr.html)

## 최근 연구 추가 확인과 범위

Zero-AVSR(ICCV 2025)은 언어에 덜 종속적인 로마자 표현과 LLM을 연결한다. MARC 82개 언어에는 한국어 128.6시간이 포함되어 있다. 따라서 ‘최근 다국어 연구에는 한국어가 전혀 없다’는 일반화는 틀리다. 그러나 이 논문의 핵심 입력은 오디오+영상이고 대표 zero-shot 표는 한국어 웹캠 입술 전용 성능을 입증하지 않는다. 현재 목적에 바로 맞는 한국어 VSR 완성품으로 추천하지 않는다. [Zero-AVSR 원문, §3·부록 데이터 표](https://arxiv.org/html/2503.06273), [저자 코드](https://github.com/JeongHun0716/zero-avsr)

2026년 연구까지 검색했지만, 검색 결과만으로 읽지 못한 본문이나 공개되지 않은 모델의 성능을 확정하지 않았다. 예를 들어 2026년의 viseme 기반 dual-stream 연구는 검색에 잡혔으나 이번 조사에서 본문 열람이 되지 않아 도입 추천의 근거에서 제외했다. 이 문서는 ‘전 세계 모든 논문을 망라한 최신 순위’가 아니라, 원문과 저자 자산을 확인한 실질적인 의사결정 자료이다.

## 권장 경로 두 가지

### 경로 A — 동일 데이터의 한국어 공식 기준선부터 검증: 우선 권장

이것은 곧바로 모델을 교체하자는 결정이 아니라, **대용량 데이터를 추가 확보하기 전에 비용이 작은 도입 가능성 검증**을 하자는 제안이다.

1. OLKAVS의 영상 전용 가중치 실제 파일, 대응 config/사전/외부 frontend, 사용 조건을 확인한다. 가중치의 입력 모달리티가 V-only인지 코드로 확인한다.
2. 별도 실험 환경에서 저자 제공 sample과 정상 확인한 짧은 한국어 영상으로 공식 입력 조건을 재현한다. 현재 프로젝트 환경이나 체크포인트를 덮어쓰지 않는다.
3. 공개 모델이 AIHub train 전체를 학습했다면, 현재 프로젝트가 TS 자료에서 따로 떼어 놓은 화자도 이미 본 화자일 수 있다. 기존 내부 heldout은 도입 작동 확인용으로만 보고, 공식 validation과 동의받아 새로 수집한 웹캠 평가를 분리한다.
4. 실제 webcam ROI를 공식 전처리와 일치시킨 뒤 문장 종료 후 추론을 붙인다. 정확도·빈 출력·엉뚱한 문장·무발화 오출력·종료 후 지연을 측정한다.
5. 여기서 도메인 차이가 확인되면 다양하게 선정한 한국어 ROI subset으로 적응한다. 전체 원본 20TB를 먼저 확보하는 순서로 돌아가지 않는다.

이 경로는 한국어 문자 체계와 데이터 도메인을 이미 학습한 자산을 활용할 수 있다는 이점이 있다. 반면 공개 가중치의 가용성·사용 조건·의존성 재현·현재 사용자 PC에서의 속도는 **아직 검증되지 않은 도입 조건**이다.

### 경로 B — 사전학습 시각 특징 + 한국어 출력기: 대안

한국어 공식 V-only 자산을 실행하기 어렵다면 Auto-AVSR 또는 AV-HuBERT 계열의 사전학습 시각 encoder를 검토한다. 처음에는 encoder를 동결하고 한국어 출력기를 학습하거나, 작은 학습률로 일부만 미세조정한다. 영어 디코더·토크나이저를 그대로 유지하지 않는다. 연구용 학기 프로젝트인지 향후 제품 배포까지 원하는지에 따라 라이선스 선택도 달라진다.

이 경로에서도 모델이 요구하는 25/30fps, RGB/grayscale, crop 정렬, 정규화, 토큰 순서를 계약처럼 고정해야 한다. 정상 원본에서 학습용 입 ROI만 일괄 생성하고 소수의 버전 관리된 shard로 보관한다. 동결 특징 캐시는 학습 비용을 줄일 수 있지만 ROI·증강·encoder를 바꾸면 재생성이 필요하므로 원본 추적 manifest를 남긴다. 이 권고는 여러 연구의 전이 방법을 현재 제약에 맞춘 설계 제안이며, 현재 PC에서 성능 개선이 실측되었다는 뜻은 아니다.

## 현재 프로젝트에 반영할 사항

| 유지할 것 | 수정할 것 | 뒤로 미룰 것 |
|---|---|---|
| 영상 전용 문장 인식 목표, 한국어 자소 표현, CTC 기준선 | 처음부터 학습하는 작은 모델만을 주력으로 삼는 전략 → 사전학습 한국어/VSR 기준선 비교 | 신규 아키텍처를 여러 개 한꺼번에 학습 |
| 시간 구간·fps·ROI·CTC 길이 검사, 실패 시 중단 | 소수 validation 반복 사용 → 더 다양한 화자/문장 validation 및 최종 독립 test | 모든 AIHub 원본과 모든 시점 선확보 |
| 파일·코드·선택 규칙 hash와 manifest, 기존 결과 보존 | 학습 ROI와 웹캠 ROI의 crop/색상/fps 차이 해소 | 성능 확인 전 언어모델로 출력 문장만 자연스럽게 교정 |
| 정지 영상·순서 섞기 등 시각 활용 대조 실험 | 평균 CER만 보기 → 화자별 CER, 음절/자소 CER 정의, WER 정규화, 무발화 오출력, 지연 병기 | 모델 증거 없이 ‘실시간 한국어 자유 대화 완성’ 주장 |

소리 없이 보이는 입 모양에는 발음 정보가 모두 담기지 않는다. 영상 품질이 나쁘거나 여러 발음이 비슷하게 보일 때 문맥 모델은 도움을 주지만, 실제로 말하지 않은 자연스러운 문장을 만들어 낼 수도 있다. 따라서 추론 UI에는 처리 중/인식 불가를 표현하고, 모델의 점수는 보정 검증 없이 ‘정확할 확률’로 표시하지 않는 것이 적절하다. 특정 단어 집합만 분류하는 짧은 데모를 만들 수는 있지만, 그것이 최종목표인 임의 한국어 문장 인식과 같다고 평가해서는 안 된다.

이번 문서는 재개 이후의 실행안을 제시한다. 사용자의 중단 요청에 따라 단계 18 이후 진행이나 새 학습은 하지 않는다.
