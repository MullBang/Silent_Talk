# 새 계획 2단계 — 입력·디코더 비교의 독립 검토

검토일: 2026-09-24. 공식 코드 커밋은 `af2feda3e3ac91ff3fef2454fcee662366ce9f4b`이다. 이 문서는 고정된 공식 소스, 1단계 wrapper와 입력 manifest, 저자 논문의 읽기 전용 검토다. 모델·데이터·공식 소스를 수정하거나 추론 결과를 새로 생성하지 않았다. 실제 비교 수치는 2단계 실행 보고서를 따른다.

**현재 증거로 checkpoint의 학습 해상도를 확정할 수 없다.** 같은 원본 구간에서 만든 96/224 입력과 원본/수정 검색, 독립 CTC greedy를 교차 비교하는 설계는 타당하다. 다만 이 비교는 기존 train 4문장의 원인 진단이며 모델 정확도나 논문 성능의 재현 평가가 아니다.

## 1. 96과 224의 근거

| 증거 | 확인한 내용 | 해석 |
|---|---|---|
| 공식 `README.md:132` | bbox crop을 96×96으로 설명 | 96 조건을 확인할 직접적인 근거 |
| 공식 `preprocess.py:26,89,108,113,124,230` | 함수·CLI 기본값이 모두 224×224 | 224 조건을 확인할 직접적인 근거 |
| `configs/v_train.yaml`, `v_inference.yaml` | 입력 공간 해상도 항목 없음 | YAML로 어느 쪽이 학습값인지 결정할 수 없음 |
| `avsr/models/resnet/resnet.py:112` | `AdaptiveAvgPool2d((1,1))` | 여러 공간 크기를 같은 특징 차원으로 바꿀 수 있어, strict loading 성공만으로 학습 크기를 알 수 없음 |
| 저자 논문 §3 | 제공 lip bbox와 발화 시간으로 자르는 절차를 설명 | 검토한 본문에 96/224 선택을 확정할 설명은 없음 |

논문은 외부 시각 사전학습을 사용하는 V-model과 처음부터 학습한 F/All-model 실험을 구분한다. 이번 `multiview_lip.pt`를 V-model의 CER 26.64%와 연결하거나, 그 모델이 썼을 것으로 추정하는 외부 전처리를 그대로 적용할 근거는 없다. [저자 논문 §3.1–3.2](https://arxiv.org/html/2301.06375)

따라서 어느 크기에서 문장이 더 잘 나오더라도 그것은 **이 checkpoint가 현재 입력 조건에 더 잘 반응했다는 관찰**이다. 실제 학습 크기를 증명하는 것은 아니다. 크기 비교 뒤에는 잠정 입력 계약을 고정하고 별도 개발 자료로 확인해야 한다.

96 영상은 기존 프로젝트의 RGB·25fps·여백 crop 캐시를 사용하면 안 된다. 같은 원본 frame index, 같은 bbox와 BGR, 같은 interpolation, 같은 mp4v 왕복 과정을 쓰고 공간 크기만 바꿔야 한다. 이미 압축된 224 영상을 다시 96으로 줄이는 방법은 별도 변환 조건이 추가되므로 원본에서 직접 만드는 방법과 구분한다. 가능하면 재생성한 224가 기존 1단계 224와 같은 프레임·입력 통계를 유지하는지도 확인한다.

근거: [고정 README](https://github.com/IIP-Sogang/olkavs-avspeech/blob/af2feda3e3ac91ff3fef2454fcee662366ce9f4b/README.md), [고정 전처리 코드](https://github.com/IIP-Sogang/olkavs-avspeech/blob/af2feda3e3ac91ff3fef2454fcee662366ce9f4b/preprocess.py), [시각 frontend](https://github.com/IIP-Sogang/olkavs-avspeech/blob/af2feda3e3ac91ff3fef2454fcee662366ce9f4b/avsr/models/resnet/resnet.py).

## 2. 1단계 입력 계약의 재검토

다음 항목에서 새로운 불일치는 찾지 못했다. 이는 전체 실행의 정확성을 보증하는 것이 아니라, 아래 경로에 한정한 코드 대조 결과다.

- **색상:** 공식 raw loader가 OpenCV BGR를 그대로 사용한다. wrapper도 BGR다. 공식 crop은 FFmpegReader의 RGB에서 RGB→BGR 변환을 한 뒤 저장하므로 최종 raw loader와 일치한다. RGB/ImageNet 방식으로 바꾸는 것은 별도 가설이다.
- **정규화:** 공식 raw loader는 전체 발화의 모든 채널·픽셀에 대해 평균을 빼고 `torch.std`로 나눈다. wrapper의 float32와 `correction=1`은 이 경로를 따른다. `/255` 유무만은 이 정규화 후 거의 상쇄되지만, 채널별 정규화나 프레임별 정규화는 다르다.
- **시간과 차원:** `B×3×T×H×W`와 시간 길이 T를 전달한다. 선택한 구간의 nominal 30fps와 native 약 29.970fps 차이는 manifest에 남아 있다. 길이 인자는 현 Conformer backend에서 padding mask로 쓰이지 않으므로 batch 1·padding 없음 조건을 유지한다.
- **모델·사전:** 전체 영상 frontend가 있고 72개 사전과 strict state loading이 대응한다. 기존 프로젝트의 69개 사전을 가져올 근거가 없다. strict loading은 학습 데이터 목록·학습 전처리·최종 성능을 증명하지 않는다.
- **시각 경로:** `encoder(video, lengths, None, None)` 다음 `medium`을 거친 특징에 CTC와 attention을 적용해야 한다. `medium`을 생략하거나 특징 512차원과 decoder 입력 256차원을 혼동하지 않는다.

공식 `sample_data/*.npy`는 외부 시각망에서 미리 추출한 512차원 특징이다. 이번 자체 frontend의 출력으로 대체해서 decoder를 검증하는 것은 올바른 대조가 아니다. 현재 모델이 만든 `medium` 이후 특징을 동일하게 재사용해 decoder만 비교하는 것은 가능하다. 이 경우 특징 추출 시간과 decoder 시간은 나눠 기록한다.

근거: [공식 raw loader](https://github.com/IIP-Sogang/olkavs-avspeech/blob/af2feda3e3ac91ff3fef2454fcee662366ce9f4b/dataset/dataset.py), [encoder](https://github.com/IIP-Sogang/olkavs-avspeech/blob/af2feda3e3ac91ff3fef2454fcee662366ce9f4b/avsr/models/encoder.py), [모델 forward](https://github.com/IIP-Sogang/olkavs-avspeech/blob/af2feda3e3ac91ff3fef2454fcee662366ce9f4b/avsr/models/model.py).

## 3. CTC 대조와 남은 공식 코드 제약

### 독립 greedy의 필수 계약

`model.decoder.ctcdecoder(inputs=features)`의 logits에서 시간별 argmax를 구하고, **연속 중복을 먼저 합친 다음 blank ID 3을 제거**한다. blank를 먼저 지우면 `[가, blank, 가]` 같은 경로를 잘못 하나로 합친다. 전체 경로와 collapse 결과를 저장한 뒤, 문자열은 공식 vocabulary와 조합 규칙으로 변환한다.

공식 `method='ctc'` 검색 호출은 이 독립 greedy를 대신하지 못한다. 공식 검색에는 사용하지 않는 attention score의 `-inf`에 0을 곱해 NaN을 만들 수 있는 경로가 있고, 실제로는 prefix search이다. 직접 argmax 진단은 원본 hybrid와 별도 이름으로 기록해야 한다.

### CTC의 EOS도 확인해야 하는 이유

공식 dataset은 `[SOS, 본문, EOS]`를 만든다. collator는 그 길이에서 1을 뺀 값을 target length로 쓰고, `train.py:197`은 `targets[:,1:]`를 attention/CTC 공통 손실에 넘긴다. 따라서 공개 학습 코드의 CTC 목표에도 **EOS=2가 포함**된다. greedy 문자열은 공식 vocabulary처럼 첫 EOS에서 끝내되, 첫 EOS 위치와 이후 collapse 토큰이 있는지 보존한다. 그렇지 않으면 조기 EOS 때문에 문장이 짧아진 현상을 볼 수 없다.

### 이번 수정 이후에도 남는 제약

1. 원본 hybrid는 진행 후보에서 pad/SOS/EOS만 제외하고 blank=3은 허용한다. 토큰 저장 공유와 상위 후보 중복을 고치는 비교에서 blank 정책까지 바꾸면 수정 영향이 섞인다. 별도 검증 없이 함께 변경하지 않는다.
2. 공식 CTC prefix 점수의 EOS는 출력층 EOS 확률을 명시적으로 더하는 방식이 아니라 현재 prefix의 종결확률로 계산된다(`search.py:394`). EOS를 포함한 공개 학습 목표와의 일관성은 후속 점수 검증 대상이다. 이것만으로 현재 가중치의 학습 방식이나 짧은 출력 원인을 확정할 수 없다.
3. 공식 prefix 계산은 확률의 곱을 사용한다. 긴 입력의 수치 안정성·EOS/blank 정책·종료 검사는 텐서 clone 및 top-k 수정만으로 검증되는 것이 아니다. 수정본을 “완전히 검증된 표준 hybrid decoder”라고 부르면 안 된다.
4. 학습 YAML의 `ctc_rate: 0.5`는 `get_criterion`에 전달되지 않는다. 공개 경로는 `Hybrid_Loss`의 기본 0.2를 사용한다. 이는 향후 재학습 설정을 명확히 할 항목이며, 지금 추론 비율 0.6을 즉시 바꿀 근거는 아니다. 공개 checkpoint가 정확히 어느 학습 코드를 썼는지도 확정되지 않았다.

이 항목들은 이번 고정 비교를 중단할 이유가 아니라, 비교의 해석 범위를 제한하는 사항이다. raw argmax blank 비율, 첫 EOS 위치, 자주 나온 토큰, 유한 logits 여부를 남기면 해상도 변화에 대한 모델 반응과 검색 이후 문제를 구분하기 쉽다.

## 4. 결과 해석과 지표

공식 CER 구현은 자소를 `grp2char`로 한국어 문자로 조합하고 앞뒤 공백을 `strip()`한 뒤 편집거리를 계산한다. **문장 내부 공백은 포함된다.** 기존 프로젝트의 자모 CER와 단순 수치 비교하면 안 된다. 이번 4개 조건 비교에서 지표를 계산한다면 같은 정답 정리, 같은 문자열 조합, 같은 단위로 통일하고 `총 편집거리 / 총 정답 문자 수`를 명시한다. 문자열 CER, 자모 토큰 오류율, WER, 완전 일치를 혼합하지 않는다. [공식 metric 구현](https://github.com/IIP-Sogang/olkavs-avspeech/blob/af2feda3e3ac91ff3fef2454fcee662366ce9f4b/avsr/utils/metric.py)

| 관찰 | 뒷받침하는 해석 | 아직 말할 수 없는 것 |
|---|---|---|
| clone/top-k 수정 뒤 EOS와 마지막 토큰만 정상화 | 재현한 검색 저장 결함이 실제 출력에 영향을 줌 | 전체 문장 오류의 원인이 해결됨 |
| 같은 해상도에서 CTC가 의미 있는 문장인데 hybrid는 짧음 | 시각 특징 이후 검색·attention·EOS 종료 경로를 우선 조사할 근거 | CTC가 모든 화자·발화에서 우수함 |
| 96에서 양쪽 출력이 함께 개선 | 현재 입력 크기에 대한 강한 민감성, 잠정 96 기준 후보 | 실제 학습 크기 확정, 웹캠 정확도 확보 |
| 모든 조건이 나쁨 | 해상도·확인한 후보 저장 결함만으로 설명 부족 | 데이터 양만 늘리면 해결됨, 공개 모델 자체가 불량임 |

표본은 train 4문장·화자 2명이며 공개 사전학습과의 중복이 불명이다. 반복 비교에 이미 노출됐으므로 이후 독립 평가에 재사용하지 않는다. 결과가 좋아도 그대로 서비스에 연결하지 않고, 입력·decoder 계약을 먼저 고정한 다음 새 화자 자료에서 확인한다. 이번 원인 분리에는 추가 대용량 AIHub 학습 데이터가 필요하지 않다.

## 5. 실행 완료 후 독립 재계산

같은 날 완료된 `results/step02.json`과 `diagnose_step02.py`, `diagnostic_utils.py`, `corrected_search.py`, 입력 준비 스크립트를 추가 검토했다. 원시 실행 결과와 계획은 수정하지 않았고, 모델 추론도 반복하지 않았다. 별도 `results/step02_metrics_audit.json`에 독립 검산을 저장했다.

다음 항목은 통과했다.

- 8개 입력과 저장된 특징·CTC logits의 해시, 차원, 유한값을 확인했다. 동일 원본 crop의 96/224 쌍, 고정된 train ID·정답·프레임 수가 일치했다.
- 저장된 logits에서 argmax를 새로 계산하고, `itertools.groupby`로 연속 중복을 합친 뒤 blank 3을 제거했다. 기록된 CTC 경로·collapse 결과와 모두 같았다.
- 원시 토큰을 공식 사전으로 다시 조합한 결과가 24개 문자열과 모두 같았다. 수정 hybrid는 8개 입력 모두 반환 길이의 마지막 위치에 EOS를 정확히 하나 포함했다.
- 재생성한 224 입력은 기존 1단계 파일과 바이트가 같았고, 원본 hybrid의 raw token도 4개 모두 재현됐다.
- 프로젝트 metric 함수를 부르지 않는 별도 전체 행렬 편집거리 구현으로 모든 문장별 지표와 합산 지표를 재계산했다. 기록된 지표는 해당 구현의 정규화 규칙과 일치했다.

**지표 명칭에는 보완이 필요했다.** 실행기의 `canonical_text`는 NFC와 앞뒤 strip에 더해 내부 연속 공백도 하나로 줄인다. 공식 CER 구현은 strip만 하므로 정확히 같은 규칙은 아니다. 독립 검산 파일은 원래 지표를 `NFC+공백 정규화 문자 CER`로 명명하고, 내부 공백을 그대로 보존하는 `NFC+strip-only 문자 CER`를 추가했다.

| 입력/방법 | 기존 공백 정규화 CER | strip-only CER | 완전 일치 |
|---|---:|---:|---:|
| 224 / 원본 hybrid | 125/136 = 91.91% | 91.91% | 0/4 |
| 224 / 수정 hybrid | 125/136 = 91.91% | 91.91% | 0/4 |
| 224 / CTC greedy | 132/136 = 97.06% | 97.06% | 0/4 |
| 96 / 원본 hybrid | 26/136 = 19.12% | 19.12% | 1/4 |
| 96 / 수정 hybrid | 24/136 = 17.65% | 17.65% | 3/4 |
| 96 / CTC greedy | 28/136 = 20.59% | 29/136 = 21.32% | 0/4 |

차이는 96 CTC 마지막 문장의 `너무  신나`에 있는 중복 공백 1개다. 주 비교인 원본/수정 hybrid의 수치와 결론은 바뀌지 않는다. 수정 hybrid의 남은 문자 오류 24개는 첫 C002 발화에 모여 있다. 다른 3문장의 완전 일치가 새 화자 일반화나 웹캠 정확도를 의미하지는 않는다.

시간 기록은 공유 encoder+medium과 decoder를 분리한 것으로, 더하더라도 영상 로딩·host 전송·웹캠 수집·발화 종료 대기는 포함하지 않는다. 첫 224 특징 추출은 별도 warmup을 하지 않았다. CTC greedy 시간은 측정하지 않았다. 96 입력의 reserved memory는 앞선 224 실행에서 남은 allocator cache를 포함하므로 96만 사용하는 프로세스의 메모리 수요라고 설명하면 안 된다.
