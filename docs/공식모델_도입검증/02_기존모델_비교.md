# 2단계: 같은 네 발화에서 기존 17단계 모델과 비교

새 계획 2단계에서 먼저 고정한 네 발화를 기존 17단계 B 종료 모델에도
입력했다. 공식 96px 수정 디코더는 3문장이 일치했고 기존 모델은 0문장이
일치했다. 다만 **모델과 각 모델의 전처리를 합친 경로의 진단**이다.
네 문장만으로 새로운 화자나 실제 웹캠에서의 성능을 판정하지 않는다.

| 경로 | 공백 포함 문자 CER | 공백 제외 문자 CER | 완전 일치 |
| --- | ---: | ---: | ---: |
| 기존 17단계 B / greedy | 116/136 = 85.29% | 98/100 = 98.00% | 0/4 |
| 기존 17단계 B / beam 10 | 116/136 = 85.29% | 99/100 = 99.00% | 0/4 |
| 공식 224px / 수정 hybrid | 125/136 = 91.91% | 94/100 = 94.00% | 0/4 |
| 공식 96px / 수정 hybrid | 24/136 = 17.65% | 19/100 = 19.00% | 3/4 |

정답과 예측 모두 NFC 및 공백 축약을 동일하게 적용했다. 전체 편집거리의
합을 전체 정답 문자 수로 나눈 corpus 문자 CER이며, 기존 17단계 보고서의
문장 평균 자모 CER와 수치 정의가 다르다. 깨진 자모의 대체 문자 `�`도
예측에서 삭제하지 않았다.

공식 사전학습 모델에서 이 발화들의 학습 포함 여부는 공개 정보로 확정하지
못했다. 따라서 이 표를 독립 평가나 동등한 학습 조건의 모델 순위로 해석하지 않는다.

## 모델·입력·재현 검증

- 기존 가중치는 `results/step17-expansion/run01/B_expand512/step_6400.pt`다.
  SHA256은 `b82d9504191fab5c72877a5bc4987c8487107dfca2dc6d6cb24520429f5115cb`이고
  크기는 13,181,343바이트다. 17단계 완료 기록의 고정 종료 가중치와 일치한다.
- 프로젝트의 `models.registry.load_model_checkpoint`를 사용했다. 토큰/구조
  검사와 strict 로딩을 통과했고, 로딩된 모든 state tensor가 체크포인트와
  정확히 같음을 추가 확인했다. compact-v1, 69클래스, FP32, eval, 패딩 없는
  batch 1로 실행했다. 추가 학습이나 서비스 연결은 하지 않았다.
- 네 기존 v4 NPZ 캐시가 모두 존재하며 명세의 SHA256과 일치했다. RGB
  96×96, 실제 시간축 기반 25fps, 20% ROI 여백, ImageNet 평균/표준편차를
  사용했다. 공식 경로는 BGR, nominal 30fps, 여백 없는 ROI와 mp4v 재인코딩,
  영상 전체 평균/표준편차이므로 입력 픽셀까지 동일한 구조 비교는 아니다.
- 네 개 모두 새로 추론했다. 기존 17단계 결과가 있는 두 문장은 greedy와
  beam 10 문자열뿐 아니라 전체 FP32 posterior까지 정확히 재현했다.
  최대 절대 차이는 0이다. 다른 두 문장은 기존 결과가 없어 이번에 처음
  이 종료 가중치로 확인한 출력이다.
- 실행 전후 네 캐시·원본 명세·체크포인트의 해시를 확인했다. 기존 코드와
  가중치 및 캐시는 수정하지 않았다.

재현 명령:

```powershell
.\.venv-gpu\Scripts\python.exe experiments/olkavs_official/compare_legacy.py
```

문장별 원시 예측, 동일 기준 CER, 학습 포함 여부, 재현 검사는
`experiments/olkavs_official/results/step02_legacy_comparison.json`에 보존했다.
이 결과는 공식 96px 경로를 다음 독립 평가의 후보로 검토할 근거이며,
일반화 성능이나 웹캠 서비스 준비가 끝났다는 근거는 아니다.
