1.2 영상 FPS 리샘플링 처리
※ 중요: OpenCV cap.set(cv2.CAP_PROP_FPS, 25)만으로는 이미 저장된 MP4 파일의 FPS가 변경되지 않는다.
업로드 영상의 원본 FPS가 25fps가 아닐 경우 반드시 타임스탬프 기반 리샘플링을 수행한다.

항목
내용
웹캠 입력
브라우저가 제공한 프레임 timestamp를 기준으로 25fps 슬롯에 재표본화한다. 카메라 요청 FPS만으로 실제 프레임 간격을 보장하지 않는다.
업로드 영상
원본 FPS를 cap.get(cv2.CAP_PROP_FPS)로 읽은 뒤, 영상 duration과 frame index 기준으로 균등 샘플링하여 25fps로 리샘플링
리샘플링 방법
target_timestamps = [i/25.0 for i in range(n_frames)]
원본 프레임 중 각 target_timestamp에 가장 가까운 프레임을 선택하는 nearest-neighbor 방식 적용
적용 범위
업로드 영상 전처리(F-MVP-02), 성능 평가(F-MVP-05) 모두 동일 방식 적용

학습용 bbox 캐시 시간축 교정 (9단계)
확인된 원본 영상의 실제 FPS는 약29.97003이고 라벨의 FPS30은 반올림값이다. 후자를 원본 프레임 인덱스 계산에 사용하면 영상 후반부에서 시간 오차가 누적된다.
`prepare_data.py`는 실제 영상 FPS·프레임 수·bbox 개수를 확인하고, 각 문장 `start_time + k/25`에 대응하는 원본 프레임을 선택한다. 선택 프레임의 실제 시각과 요청 시각이 허용 오차 안인지 검사하며, bbox도 선택한 실제 프레임 인덱스로 조회한다.
캐시 NPZ 및 완성 명세 row에 `temporal_method=video-cfr-timestamps-v1`, `video_fps`, `label_fps`를 기록한다. 정책·row·NPZ의 버전과 FPS가 일치하지 않으면 사용하지 않는다. 시간 메타데이터 없는 legacy 명세는 legacy 캐시 재현에만 허용하며 새 시간축 캐시와의 혼합은 거부한다.

F-2ND-02  |  V-VAD 발화 구간 감지 (캘리브레이션 포함)  [2차 목표]

항목
내용
기능 설명
동적 임계값 기반 발화 구간 자동 감지. 시작 시 환경 캘리브레이션으로 정적 임계값의 한계를 극복한다.
d_raw 계산 정의
윗입술 중심점 (내측 상단 랜드마크 [13,14,312,311,310,415]의 평균 좌표)
아랫입술 중심점 (내측 하단 랜드마크 [17,18,84,181,180,314]의 평균 좌표)
d_raw = 두 중심점 사이의 유클리드 거리 (픽셀 단위)
mouth_ratio
mouth_ratio = d_raw / W  (W: 좌우 광대 랜드마크 간 거리 — 카메라 거리 변화 대응)
Phase 1: 캘리브레이션 (1.5초)
① 시작 후 1.5초 침묵 상태에서 mouth_ratio 시계열 수집
② baseline_mean, baseline_std 측정
③ T_open = mean + max(2×std,0.002) | T_close = mean + max(0.8×std,0.001) | T_var = max(var×1.5,0.000001). 무변화 표본에서도 임계값이 완전히 0이 되지 않도록 하한 적용. 실카메라 튜닝은 후속 측정.
→ 캘리브레이션 실패 시 기본값 사용 (T_open=0.08, T_close=0.04, T_var=0.0003) + 경고
Phase 2: 감지 루프
EMA smoothing(α=0.3) → smooth_ratio > T_open AND σ² > T_var → 발화 시작
smooth_ratio < T_close가 12프레임(0.5초) 지속 → 발화 종료
최소 발화 길이 0.5초 미만 무시
예외: 다중 화자
바운딩 박스 면적 최대 1인 추적
예외: 3프레임 연속 미검출
진행 중 발화를 취소하고 경고한다. 짧은 1~2프레임 누락은 마지막 유효 ROI로 보완한다.

is_final=false: 현재 라인 회색 텍스트 실시간 갱신
is_final=true: 현재 라인 흰색 확정 + 새 라인 준비
최근 5개 구간 스택
완료 기준 (DoD)
연속 1분 이상 자막 정상 표출 + 중간 예측 → 최종 확정 흐름 정상 동작

4.1 제어 메시지 — 프로토콜 v2 (2026-09-17 수정)
프론트엔드와 백엔드를 함께 갱신한다. frame_count 없는 구형 메시지는 거부한다.

// 세션 시작. SESSION_READY를 받은 뒤에만 프레임을 보낸다.
{"type":"SESSION_START","protocol_version":2,"session_id":"uuid-v4","client_ts":1718000000000}

// 11프레임 청크: 타임스탬프는 세션 내 실제 영상 시간축(ms), 종료 시각은 배타적.
{"type":"CHUNK_START","chunk_id":1,"utterance_id":1,"frame_count":11,"window_start_ms":0,"window_end_ms":440,"is_final":false}
// 다음 3프레임을 모두 받은 뒤 최종 추론.
{"type":"CHUNK_START","chunk_id":2,"utterance_id":1,"frame_count":3,"window_start_ms":440,"window_end_ms":560,"is_final":true}
// 마지막 데이터가 이미 전송되었다면 frame_count=0, start=end인 final로 확정한다.
// 추적 실패 시 서버에 남은 발화 취소.
{"type":"UTTERANCE_ABORT","utterance_id":2}
// 정지 버튼은 마지막 final 응답을 받은 뒤 세션 종료. 서버도 잔여 발화를 최종화한다.
{"type":"SESSION_END"}

chunk_id는 연결 내 1부터 연속 증가, utterance_id는 새 발화마다 증가한다.
0<=frame_count<=11, end-start=frame_count*40. 빈 청크는 진행 중 발화의 final만 허용.
한 발화 안의 시간 범위는 연속이어야 하며 다른 발화의 프레임과 섞지 않는다.
제어/바이너리 chunk_id 불일치·누락·중복·시간 역전·상한 초과는 오류 후 연결 종료.

4.2 프레임 데이터 메시지 (Binary ArrayBuffer)
[0~3] chunk_id (Uint32 Big-Endian), [4] 0x01, [5~7] reserved=0.
[8~] RGB Uint8 96×96×3=27,648B. 전체 메시지는 27,656B.
서버에서 float32로 바꾸어 /255 및 ImageNet mean/std 정규화를 적용한다.
한 binary는 한 프레임이며, 선언한 frame_count개를 모두 수신한 뒤 한 번 추론한다.
모델 작업은 이벤트 루프 밖의 스레드에서 실행하고 모델 실행 간 메모리 경쟁을 직렬화한다.

4.3 서버 응답
{"type":"SESSION_READY","session_id":"uuid-v4","protocol_version":2,"fps":25,"chunk_frames":11,"max_utterance_frames":200}
{"type":"PARTIAL","session_id":"uuid-v4","utterance_id":1,"chunk_id":1,"text":"안녕하","confidence":null,"is_final":false,"frame_count":11,"window_end_ms":440}
{"type":"PARTIAL","session_id":"uuid-v4","utterance_id":1,"chunk_id":2,"text":"안녕하세요","confidence":0.91,"is_final":true,"frame_count":14,"window_end_ms":560}
{"type":"ABORTED","utterance_id":2}
{"type":"ERROR","code":"MODEL_NOT_READY","message":"학습된 v2 모델이 아직 없습니다.","fatal":true}
{"type":"SESSION_END","total_segments":1,"total_frames":14}

PARTIAL의 frame_count는 발화 누적 프레임 수이다. total_segments는 확정 발화 수이다.
자막은 session_id와 utterance_id로 구분하며 늦은 응답이 다음 발화 자막을 덮어쓰지 않도록 한다.
서버 응답이 30초 이상 없거나 대기 프레임이 200개를 넘으면 사용자에게 알리고 중단한다.
현재 검증은 모델 대체 통신·수명주기 검증이며, 실제 인식 정확도·1초 이내 지연 달성을 뜻하지 않는다.

);

**2026-09-18 개선12단계 — 16문장 유지 / 64문장 확대 학습 진단 완료**

12단계 학습 전환 진단을 완료했습니다. 같은 경량 가중치에서 16문장 유지/64문장 확대를 각각 1,600회 시도했습니다. 유지군은 기존 16개를 계속 복원했고, 확대군은 25회 평가에서 9/16으로 낮아졌다가 최종 16/16로 회복했습니다. 확대군의 추가 48개 greedy CER는 104.72%→49.23%, 완전 일치 4/48입니다. 학습 표본에 대한 결과이며 val/test·실제 웹캠 성능은 이번에 평가하지 않았습니다. 12단계 당시 제안한 같은64개 학습량 확대 실험의 완료 결과는 아래13단계에 기록했습니다. 현재는 추가 다운로드가 필요하지 않으며, 필요해지면 종류·규모·이유를 먼저 안내합니다.

두 군은 같은 v4 train의 short16 가중치·새 Adam·lr 0.0003·batch 2·AMP·clip 1·seed42에서 시작했다. 추가 48개는 예측을 보지 않고 train 화자×길이 구간에서 사전 선정했다. 각 1,600회 시도로 A는 표본당 200회, B는 50회 제시했다. 성공 갱신은 A 1,600/B 1,599회이며 B의 49회에 비유한 기울기를 건너뛰고 가중치가 그대로 유지된 것을 확인했다. 이 skip은 최초 복원 저하 관측 25회보다 뒤다. 확대군의 기존 문장 복원은 일시적으로 낮아졌다가 회복했으며 이번 64개 실험의 최종 시점에는 기존 문장 복원 실패가 나타나지 않았다. 1,000문장 학습의 원인이 해결됐다는 뜻은 아니다.

B 최종 추가 48개의 정상/정지/순서섞기42 greedy CER는 49.23%/60.51%/57.46%, 완전 일치는 4/48·1/48·0/48이다. 기존 16은 정상 16/16이지만 정지 9/16·섞기 10/16도 복원한다. 정상 입력의 이점은 관찰했으나 정적 단서·길이·암기와 일반화는 분리되지 않았다. 실제 웹캠 서비스에는 배포하지 않았다.

새 진단 코드는 매 시도마다 unscale 후 clip 전·후 기울기, 실제 가중치 변화, scaler·skip·표본 노출을 저장한다. 신규 관련 78개 검사 통과(선정·계측 23, 실행기 13, 집계 42) 및 원시 posterior 2,240행 재계산을 완료했다. 전체 프로젝트 검사 재실행은 아니다. 모델 구조·입력 전처리·토큰 사전·웹캠 프로토콜은 이번 단계에서 변경하지 않았다.

12단계 당시에는 같은64개로 총6,400회 등 고정 예산을 비교하는 후속 실험을 제안했다. 12단계 스냅샷에는 optimizer/scaler/RNG가 없어 원래16개 가중치부터 앞1,600회를 재현해야 했다. 이 재현과 연속 학습 결과 및 새 재개 상태 저장은 아래13단계에 기록했다.

17단계 256개 추가 학습/512개 자료 확대 비교를 완료했습니다. 종료 A/B의 문장 평균 greedy 자모 CER는 미학습 60개에서 81.57% / 79.44%, 다른 화자의 개발 검증 20개에서 80.02% / 78.03%입니다. 512개 확대군은 256개 유지군보다 고정 미학습 두 집단의 문장 평균 CER가 낮았지만, 출발점 대비 개선은 약 0.81·0.20%포인트에 그쳤다. 평가 80문장의 완전 일치는 여전히 0개이며, 정상 프레임 순서의 이점도 일관되지 않았다. 같은 자료의 추가 반복이나 같은 녹화 안의 문장 확대만으로 웹캠 문장 인식 목표에 도달하지 못했다. 다음 단계 제안은 아래 17단계 기록에 있습니다.

16단계 B의 누적 12,800회 전체 상태에서 두 군을 출발시켰다. 원본 파일의 로컬 3,200회와 누적 이력을 구분해 출발 성공 12,797회·생략 3회를 연결했고, 실제 Adam 상태를 보존했다. 두 군 모두 학습률 0.0001·batch 2·추가 6,400회 시도로 누적 19,200회까지 진행했다.

| 상태 | 미학습 60개 CER / 일치 | 개발 검증 20개 CER / 일치 |
| --- | ---: | ---: |
| 공통 출발: 16단계 B | 80.26% / 0/60 | 78.23% / 0/20 |
| A: 256개 유지 | 81.57% / 0/60 | 80.02% / 0/20 |
| B: 512개 확대 | 79.44% / 0/60 | 78.03% / 0/20 |

617개 후보에서 기존 64+192개를 순서대로 보존하고 남은 361개 중 256개를 예측 없이 추가했다. 추가 길이 구간은 0/111/111/34개, 총 512개는 28/187/187/110개다. 두 군 모두 기존 8명·59개 녹화로 새 화자나 녹화가 늘어난 실험은 아니다. 문장당 추가 제시는 A 50회, B 25회이며 프레임 계산량도 달랐다. 새 256개는 B의 학습 자료이므로 그 적합도와 고정 미학습 60+20개의 성능을 구분했다.

정상 입력은 로컬 0/1,600/3,200/6,400회에 평가했다. 정지·순서 섞기는 미학습 80개의 출발·종료에만, beam10은 정상 592개의 출발·종료에만 적용했다. posterior 5,376개 재계산, beam 2,368개 재디코딩, 전체 상태 8개 검사 및 관련 테스트 172개가 통과했다. 로컬/누적 성공·생략과 프레임 제시 수는 상세 보고서에 기록했다.

한 seed의 개발 비교이며 문장 수 외에 길이·반복 빈도·계산량도 달랐다. 검증 점수로 가중치 선정·기존 체크포인트 교체·test50 캐시 접근·웹캠 평가·서비스 배포는 하지 않았다. CER의 보수를 프로그램 정확도로 환산하지 않는다.

17단계 당시 제안한 다음 18단계는 새 화자·새 녹화의 Training 원본 영상과 대응 JSON 라벨을 확보하기 위한 수집 요건과 입력 검수 준비를 우선한다. 현재 확인한 로컬 Training 원본(TS1/TS10, TL1/TL10)에는 기존 학습 8명의 새 녹화나 별도의 새 학습 화자가 없었다. 나머지 두 화자는 기존 val로 남겨야 한다. 다른 각도나 같은 녹화의 추가 문장은 남아 있지만 화자·녹화 다양성을 늘리지는 않는다. 따라서 이 범위를 넓히는 학습에는 추가 자료가 필요하다. 우선 기존 train/val/test 화자와 겹치지 않는 새 Training 화자의 영상·JSON을 첫 검수용 소량 표본으로 준비하고, 메타데이터로 화자·녹화·정답 중복을 확인한 뒤 실제 FPS, 발화 구간, 입술 ROI와 추출 품질을 검수하는 순서가 적절하다. 새 자료를 학습에 넣기 전에 분할과 비교 계획을 고정하고 본 학습에 필요한 화자·녹화 수는 18단계 수집 요건에서 정한다. 기존 ROI 좌표 교정과 9단계 FPS 교정, 11·15~17단계 대조를 오류 징후 없이 반복하는 작업은 우선하지 않는다. 이번 결과만으로 데이터 부족을 유일 원인으로 확정하거나 새 자료만으로 해결된다고 단정할 수는 없으며, 모델 표현력·정규화 등의 영향은 별도 통제 비교가 필요하다.

17단계 종료 당시에는 18단계를 아직 실행하지 않았다. 17단계는 기존 자료로 완료했으며 위 제안의 새 화자·녹화 학습에는 추가 Training 영상과 대응 JSON이 필요하다.

## 18단계 — 신규 원본 무결성 점검 후 복구 대기

TS2·TS20·TS200에서 기존 화자와 겹치지 않는 신규 15명의 6,255문장 메타데이터 후보를 확인하고, 별도 입력 검수용으로 120문장·30영상을 선정했다. 이 숫자는 라벨 기반 후보와 검수 계획의 규모이며, 사용할 수 있는 영상이나 추출 완료 클립의 수가 아니다.

| 검사 범위 | MP4 내부 박스가 파일 끝을 초과 | 0바이트 파일 | 구조 검사만 통과 |
| --- | ---: | ---: | ---: |
| 신규 정면 영상 180개 | 161개 | 2개 | 17개 |
| 선정 파일럿 영상 30개 | 28개 | 0개 | 2개 |

0바이트 파일 2개는 필수 `ftyp` 헤더도 없었다. 구조 통과는 MP4 상위 박스 경계 확인 결과이며, 정상 재생·전체 디코딩·발화 구간 및 ROI 검증을 통과했다는 뜻은 아니다. 현재 생성된 파일럿 클립은 **0개**이고 새 자료의 학습·모델 추론은 실행하지 않았다.

먼저 불완전한 원본의 완전한 사본을 확보하고 파일 크기·해시·컨테이너 구조·디코딩을 다시 확인해야 한다. 이후 기존에 고정한 120문장 계획에 따라 시간축·입술 ROI를 검수한다. 구조만 통과한 일부 영상으로 기존 계획을 대체하지 않았으며, 17단계 체크포인트·성능 기록과 기본 `aihub_timed_v4` 명세도 유지한다.
