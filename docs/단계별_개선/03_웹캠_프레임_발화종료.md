# 3단계 완료: 웹캠 프레임 전송과 발화 종료 처리

작업일: 2026-09-17

웹캠의 실제 영상 시각을 25fps로 맞추고, 청크의 모든 프레임을 수신한 뒤 추론하도록 프론트엔드와 백엔드를 함께 수정했다. 발화 종료·정지·추적 실패·연결 종료의 상태를 구분하고 자동 검사, 실제 WebSocket 통신, 브라우저 수명주기 검증을 마쳤다.

**실제 입술 인식 정확도와 지연을 검증한 단계는 아니다.** 아직 학습된 `baseline_jamo_v2.pt`가 없으므로 실제 자막 인식에는 이후 모델 학습이 필요하다.

## 수정한 문제

| 기존 문제 | 수정 결과 |
|---|---|
| 최종 청크의 첫 프레임만 받고 확정하여 나머지 프레임이 누락됨 | `frame_count`개를 모두 수신한 뒤 한 번만 추론·확정 |
| 마지막 청크가 비어 있으면 누적 발화가 확정되지 않음 | `frame_count=0, is_final=true` 제어 메시지만으로 최종화 |
| 정지 버튼이 남은 발화를 버리고 즉시 소켓을 닫음 | 촬영은 즉시 종료하고 마지막 결과 수신 후 세션 종료 |
| 화면 갱신 주기를 카메라 프레임 속도처럼 처리함 | 실제 영상 시각으로 40ms 간격의 25fps 입력 구성 |
| 청크 시작·종료 시각이 항상 0 | 프레임의 세션 내 시각과 프레임 수를 실제로 기록·검사 |
| 발화 감지 프레임과 감지 직전 영상이 빠짐 | 시작 프레임을 포함한 최대 8프레임 보존 |
| 매 프레임마다 전체 누적 영상을 추론함 | 청크당 한 번으로 변경, 모델 연산을 이벤트 루프 밖에서 실행 |
| 서버가 느리면 브라우저·서버에 영상이 계속 쌓일 수 있음 | 응답 후 다음 청크 전송, 발화·대기 버퍼 상한 적용 |
| 재시작·초기화 취소 때 이전 상태나 장치가 남을 수 있음 | 새 세션 상태 생성, 늦게 도착한 카메라/랜드마크 자원도 해제 |
| 서버 오류가 얼굴 검출 경고로 보이거나 모달의 상세 메시지가 무시됨 | 미학습·서버 장애·프로토콜 오류의 구체적인 이유 표시 |

## 실제 처리 방식과 제한

### 영상 시간축과 입술 영역

`requestVideoFrameCallback`의 영상 시각을 우선 사용한다. 이를 지원하지 않는 브라우저에서는 rAF와 `video.currentTime`을 함께 사용하여 같은 영상 프레임을 반복 처리하지 않는다. 인접한 두 원본 시각 중 목표 시각에 가까운 프레임을 선택하는 방식으로 25fps 입력을 구성한다. 실제 프레임 콜백과 시각 정보의 의미는 [MDN 문서](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)에 따른다.

15fps 입력에서는 일부 프레임이 반복될 수 있다. 25fps로 배열을 구성한다고 촬영에서 놓친 입술 움직임을 복원하는 것은 아니다. 200ms를 넘는 촬영 공백은 많은 정지 프레임으로 채우지 않고 진행 중 발화를 취소한다.

ROI는 RGB Uint8 96×96, 여백 20% 규칙을 유지한다. 프론트의 bbox 좌표 반올림을 백엔드와 같은 floor/ceil 방향으로 맞췄다. 입 벌림 비율은 영상의 가로·세로 픽셀 크기를 반영하도록 수정했다. 화면의 미러링은 표시용이며 전송 영상에 적용하지 않는다. 마이크 입력은 요청하지 않는다.

웹캠은 한 명의 얼굴을 대상으로 한다. MediaPipe 실제 검출 품질과 AI Hub 라벨 bbox 사이의 분포 차이는 별도 실험이 필요하다. MediaPipe 검출 호출 자체는 여전히 브라우저 메인 스레드에서 수행한다. 실제 기기에서 부담이 크면 후속 성능 단계에서 Worker 분리 등을 검토한다. [MediaPipe 웹 가이드](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/web_js)에도 동기 검출 호출의 실행 특성이 설명되어 있다.

### 발화 구간

- 시작 시 약 1.5초의 무발화 상태로 임계값을 보정한다. 표본이 부족하면 기본 임계값과 경고를 사용한다.
- 시작 프레임 포함 최대 8프레임을 보존한다. 즉 감지 시점보다 최대 7프레임·280ms 앞의 영상까지 포함한다.
- 최소 12프레임의 발화를 확인한 다음 전송하여 짧은 오검출이 서버 버퍼에 남지 않도록 한다.
- 입이 닫힌 상태가 12프레임 지속되거나 사용자가 정지를 누르면 남은 발화를 확정한다.
- 한 발화는 최대 200프레임·8초다. 계속 말하면 이 상한에서 구간을 나눈다. 단어 경계에서 나눈다는 보장은 없다.
- 1~2프레임의 얼굴 추적 누락은 마지막 유효 ROI로 보완한다. 3프레임 연속 누락은 진행 중 발화를 취소하고 자막을 제거한다.
- 연결이 끊기면 자원을 해제하고 재시작을 안내한다. 끊기기 전 영상과 새 영상을 같은 발화로 이어 붙이지 않는다.

V-VAD 임계값의 실제 화자별 적합성은 아직 측정하지 않았다. 이 구현이 모든 짧은 단어나 모든 발화를 정확히 검출한다는 뜻은 아니다.

### 전송과 추론

프로토콜 버전은 **2**다. 프론트엔드와 백엔드를 함께 갱신해야 한다.

1. `SESSION_START`에 버전을 전달한다. 서버는 호환되는 학습 모델을 확인하고 `SESSION_READY`로 응답한다.
2. `CHUNK_START`에는 청크 ID, 발화 ID, 프레임 수, 시작·종료 시각, 최종 여부를 넣는다.
3. 선언한 개수만큼 바이너리 프레임을 보낸다. 청크당 최대 11개이며 프레임당 헤더 8B + RGB 27,648B다.
4. 서버는 모든 프레임을 받으면 한 번 추론하고 `PARTIAL`을 보낸다. 최종 청크도 같은 규칙을 따른다.
5. 프론트는 해당 응답을 받은 후 다음 청크를 전송한다. 빈 최종 청크도 응답을 기다린다.
6. 정지 시 마지막 최종 응답 후 `SESSION_END`를 보낸다. 서버도 세션 종료 시 잔여 발화가 있으면 최종화한다.

청크 ID와 헤더, 순서, 발화 ID, 시간 연속성, 데이터 크기를 검사한다. 프레임 수가 모자란 청크를 다음 제어 메시지로 덮어쓰지 않는다. 오류 후 버퍼를 재사용하지 않고 연결을 정리한다.

서버의 발화 버퍼는 200프레임, 프론트의 전송 대기도 200프레임으로 제한한다. 응답 대기 30초를 넘기거나 전송 대기 상한을 초과하면 원인을 알리고 중단한다. 이 상한은 모델 실행에 필요한 전체 RAM/VRAM을 제한하는 값은 아니다. 무거운 기존 모델의 연산·메모리 문제는 다음 단계에서 다룬다.

## 검증 결과

| 검증 | 결과 | 범위 |
|---|---|---|
| Python 자동 검사 | **175개 통과** | 기존 회귀 검사와 웹캠 프로토콜·버퍼·종료·오류 처리 |
| MediaPipe 의존 기존 검사 | 2개 선택 제외 | 현재 Python 검증 환경에 MediaPipe 미설치 |
| 프론트 자동 검사 | **19개 통과** | 15/25/30/60fps 리샘플, 시작 버퍼, 빈 종료, 순서, 대기 상한 등 |
| 프론트 배포 빌드 | 통과 | Vite production build |
| 실제 Node → FastAPI WebSocket | 통과 | 2개 발화·27프레임, 수신 배열의 SHA-256 일치 |
| Headless Edge 화면 검사 | 5개 시나리오 통과 | 실제 React 화면·영상 콜백·시작/정지·자원 정리 |

WebSocket 검사는 첫 발화 11프레임 뒤 빈 final, 두 번째 발화 11+5프레임의 final을 전송했다. 서버 추론 호출은 정확히 4회였으며 각 최종 배열의 해시가 전송 원본과 일치했다. 모델은 해시 계산 함수로 대체했다. 영상 프레임은 합성 데이터이며 학습용 데이터를 추가로 요구하지 않았다.

브라우저 검사는 다음을 실행했다.

- 모델 미학습 이유가 모달에 표시되고 카메라 권한을 요청하지 않음.
- 캘리브레이션 → 중간 자막 → 정지 → 최종 자막 → 카메라/검출기 해제.
- 재시작 후 새 상태를 사용하고, 연결 끊김 시 미확정 자막 제거와 안내.
- 카메라 권한 처리 중 정지해도 뒤늦게 생성된 영상 트랙이 종료됨.
- 모델 초기화 중 페이지를 떠나도 나중에 생성된 검출기와 카메라가 해제됨.

카메라는 Canvas 스트림, 랜드마크 검출과 서버 자막은 테스트용 대체물을 사용했다. **실제 사용자 카메라·입술 검출·학습 모델의 인식 정확도 또는 지연을 입증하는 검사는 아니다.**

## 재실행과 파일

프로젝트 루트의 PowerShell:

```powershell
$env:OMP_NUM_THREADS = '2'
$env:MKL_NUM_THREADS = '2'
& '.\.venv-tokenizer\Scripts\python.exe' -m pytest backend/tests -q -k 'not test_no_face_segment_returns_none and not test_extract_empty_raises'
& '.\.venv-tokenizer\Scripts\python.exe' scripts/verify_webcam_wire.py
cd frontend
npm.cmd test
npm.cmd run build
```

브라우저 검사는 개발 서버를 5175 포트로 실행하고 `frontend/tests/webcamPage.browser.cjs`를 사용한다. Playwright가 별도 위치에 있으면 `PLAYWRIGHT_PATH`에 패키지 경로를 설정한다. 현재 실행 결과는 [검증 요약 JSON](03_검증결과.json)에 모았다.

주요 변경 파일:

- `frontend/src/webcamStream.js`: 리샘플링·발화·전송 상태.
- `frontend/src/pages/WebcamPage.jsx`: 카메라/랜드마크 수명주기와 화면 연결.
- `frontend/src/webcamUtils.js`, `constants.js`: 입술 비율·좌표·프레임 포맷과 상수.
- `frontend/src/components/ErrorModal.jsx`: 구체적인 오류 메시지 표시.
- `backend/services/ws_handler.py`: 프로토콜 v2·청크 경계·추론·종료.
- `scripts/verify_webcam_wire.py`: 로컬 실제 송수신 검증 도구.
- Python·프론트·브라우저 회귀 테스트 및 README·설계서·기획서 갱신.

검증용 환경에 uvicorn과 websockets를 추가했다. GPU 학습 환경을 설치하거나 모델을 학습한 것은 아니다. 원본 데이터와 1·2단계 캐시, 기존 가중치는 유지했다.

## 추가 데이터와 다음 단계

**이번 단계에는 추가 학습 데이터가 필요하지 않았다.** 사용자의 요청에 따라 이후 단계에서 데이터 추가 확보가 필요해지면 필요한 종류·규모·이유를 먼저 알린다.

현재 15명·150문장 파일럿은 후속 소규모 학습 연결 확인에 사용할 수 있다. 다양한 사람의 한국어 자유 발화 인식에 충분한 학습 규모라는 뜻은 아니다. 실제 웹캠 성능 검증 단계에서는 학습에 사용하지 않은 화자의 웹캠 영상과 정답 문장도 필요할 수 있으며, 필요 시 해당 단계에서 구체적으로 안내한다.

다음 **4단계는 모델 구조와 GPU 학습 환경 개선**이다. 현재 큰 LSTM 입력과 메모리 부담을 줄이고 RTX 3080 환경에서 소규모 실행을 확인한 다음 실제 학습으로 진행한다.
