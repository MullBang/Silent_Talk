# 18단계 — 신규 자료 무결성 점검 및 복구

작성일: 2026-09-24. **자료 점검은 완료했지만 원본 재확보가 필요해 전처리와 학습은 진행하지 못했다.** 신규 학습 클립 생성은 0개이며, 기존 데이터와 모델을 변경하지 않았다.

## 영상이 열리지 않는 이유

새 TS2·TS20·TS200의 정면(A) 영상 180개를 MP4 최상위 박스 구조로 검사했다. 161개는 파일 내부에 선언된 박스 끝 위치가 실제 파일 끝을 넘었고, 2개는 0바이트였다. 나머지 17개는 이 구조 검사만 통과했다. 17개의 전체 프레임 디코딩·라벨 정렬·입술 영역 검수는 아직 하지 않았으므로 정상 학습 영상으로 확정하지 않는다.

| 원천 압축 묶음 | 검사 수 | 선언 길이보다 파일이 짧음 | 0바이트 | 구조 검사만 통과 |
|---|---:|---:|---:|---:|
| TS2 | 60 | 54 | 1 | 5 |
| TS20 | 60 | 51 | 0 | 9 |
| TS200 | 60 | 56 | 1 | 3 |
| 합계 | 180 | 161 | 2 | 17 |

검사 범위는 새 세 묶음의 정면 영상이다. 전체 각도 영상 900개의 손상률이나 다른 기존 자료의 상태로 일반화하지 않는다. 검사 프로그램이 직접 읽은 박스 헤더는 합계 4,408바이트이지만, Google Drive 프로그램이 내부적으로 내려받은 양은 측정하지 않았다.

첫 전처리 대상 `lip_J_1_F_02_C040_A_001.mp4`의 근거는 다음과 같다.

- 실제 크기: **18,874,368바이트(18MiB)**.
- 영상 데이터 `mdat` 박스가 선언한 끝 위치: **348,888,707바이트**. 선언대로라면 최소 **330,014,339바이트**가 부족하다. 이는 최종 정상 파일 크기의 확정값이 아니다.
- 현재 G: 파일과 프로젝트에 복사한 파일의 SHA-256이 `894ea6436a945c2bb9870b413afd25c704eaeef60d5c69608d029ddb76696556`으로 일치했다. 이번 로컬 복사에서 내용이 바뀐 것은 아니다.
- OpenCV/FFmpeg는 `moov atom not found`로 영상 열기에 실패했다.

따라서 현재 사본의 MP4 구조가 불완전하거나 내부 길이 정보와 모순되는 것은 확인했다. **처음 다운로드, 분할 압축 병합, 압축 해제, 업로드, 동기화 중 어느 지점에서 문제가 생겼는지는 확인할 수 없다.** 다수의 짧은 파일과 0바이트 파일은 불완전한 파일 생성·전송 가능성을 뒷받침하지만, Google Drive가 원인이라고 단정할 근거는 없다.

코덱 설치나 확장자 변경은 파일에 없는 영상 바이트를 만들 수 없다. 일부 영상 조각을 재생 가능하게 만드는 수선도 원래 문장 전체와 라벨 정렬을 보장하지 않으므로 학습 원본의 복구로 취급하지 않는다.

## 복구 경로 확인 결과

사용자는 C:의 원본 압축파일과 업로드 전 사본을 이미 삭제했고 Google Drive 파일만 남아 있다고 확인했다. Drive 웹에서 위 대표 파일의 **파일 정보 → 버전 관리**를 확인했으나 현재 버전 하나만 표시되었다. 이 파일에는 화면에서 선택 가능한 이전 버전이 없었다. 다른 179개 파일의 버전 이력은 확인하지 않았다.

지금 실행 가능한 복구 경로는 AIHub에서 완전한 원천 압축파일을 다시 받는 것이다. [공식 데이터 페이지](https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=538)의 파일 목록에서 다음을 확인했다. 용량은 사이트 표시값이며 정확한 바이트 수나 체크섬으로 대체해 해석하지 않는다.

| 순서 | 파일 | 표시 용량 | 파일 키 |
|---|---|---:|---:|
| 1 | TS2.tar | 78.83 GB | 54972 |
| 2 | TS20.tar | 86.80 GB | 54973 |
| 3 | TS200.tar | 88.50 GB | 54974 |

전체 데이터셋은 받지 않는다. 이미 복사한 정면 JSON 180개는 파싱과 후보 인덱스 생성을 통과했으므로 첫 복구 대상은 원천 영상이다. 영상 복구 후 라벨과의 대응을 다시 검사한다.

공간 확인 시 C: 여유는 217,345,482,752바이트(약 202.42GiB), D:는 450,703,523,840바이트(약 419.75GiB)였다. D:에 다음 폴더를 만들었다.

```text
D:\lipnet_recovery\stage18\downloads
D:\lipnet_recovery\stage18\verified
```

세 묶음을 한꺼번에 압축 해제하면 원본 압축파일과 해제본이 공간을 크게 사용하므로 **한 묶음씩 다운로드 → 검사 → 필요한 정면 영상 추출** 순서로 진행한다. AIHub Shell 공식 문서도 다운로드 용량의 2~3배 여유 공간을 권장한다. 공간 수치는 실행 시 다시 확인해야 한다. [AIHub API/Shell 안내](https://www.aihub.or.kr/devsport/apishell/list.do)

AIHub 로그인 화면까지 준비한 뒤 사용자가 **직접 다운로드할 예정**이라고 답했다. 에이전트는 다운로드를 시작하지 않았으며 완료 여부도 아직 확인하지 않았다. Windows 다운로드 관리자의 저장 위치를 위 `downloads`로 지정하고 TS2.tar 한 개부터 받는다. 공식 INNORIX 안내는 전송 중지·전송 재개 기능을 제공한다. 창을 닫는 동작은 전송 이력이 사라져 재시작이 필요할 수 있으므로 중단이 필요하면 해당 기능을 사용한다. [AIHub 이어받기 안내](https://aihub.or.kr/aihubnews/notice/view.do?currMenu=131&nttSn=10129&topMenu=103)

## 재확보 뒤 검사와 18단계 재개 순서

1. 다운로드 완료 표시와 실제 파일 크기를 확인한다. 여러 조각으로 받았다면 해당 형식의 공식 병합 절차를 적용한다. 확장자만 바꾸거나 일부 조각만 해제하지 않는다.
2. 압축파일 목록·헤더·멤버 경계와 실제 읽기를 검사한다. TAR 목록을 열 수 있다는 사실만으로 압축 안 영상이 정상이라고 판단하지 않는다.
3. 대표 손상 영상과 선정된 정면 영상을 `verified`에 별도로 추출한다. 기존 G: 원본은 그대로 보존한다.
4. MP4 구조 검사 후 실제 프레임 디코딩, 해상도·실제 FPS·프레임 수·문장 시간 범위·라벨 좌표 대응을 확인한다. 파일 해시는 이후 복사 내용의 동일성 근거로 남기며, 해시 자체를 정상 영상의 증거로 삼지 않는다.
5. 검증된 원본을 대상으로 새 인벤토리와 별도 실행 기록을 만든다. 실패한 `run01`과 선정 기록은 보존하며, 실패 영상을 통과 영상으로 조용히 바꾸지 않는다.
6. 120문장 파일럿의 전처리·ROI 시각 검수·자료 분리 검사를 완료한 뒤 학습 단계로 넘어간다. 다운로드 중이거나 구조 검사만 통과한 영상을 학습에 넣지 않는다.

이번 단계는 자료 확보와 준비 상태 확인이다. 실시간 웹캠 문장 인식 성능이 개선됐다는 결과는 없다.

## 이번 단계에서 준비한 내용

기존 TS1·TS10 및 Validation 자료와 새 묶음의 파일 목록을 구분했다. 새 TS2·TS20·TS200에는 각각 영상 300개·JSON 300개·WAV 60개가 있었고, 신규 화자 15명의 정면 영상·JSON 쌍 180개를 대상으로 후보를 만들었다. 원천 WAV는 학습 입력으로 사용하지 않았다.

라벨·길이·CTC 조건을 통과한 **6,255개는 메타데이터상의 문장 후보**다. 정상 영상이 확보됐다는 뜻이 아니다. 기존 화자·녹화·문장 및 평가 자료와의 겹침을 막는 고정 규칙으로 120문장을 선정했다.

- 신규 학습: 12명 × 2녹화 × 4문장 = 96문장.
- 신규 개발 검증: C040·C059·C769, 3명 × 2녹화 × 4문장 = 24문장.
- 선정 영상 30개 중 **28개가 구조 검사 실패**, 2개만 구조 검사 통과였다. 개발 검증용 선정 영상 6개는 모두 실패했다.
- 실제 준비는 첫 영상 열기 실패에서 중단했다. 생성 클립 0개, 완료된 `intake_manifest.json` 없음.

관련 코드 검사 결과는 선택 규칙 70개, 신규 자료 준비 52개, 기존 전처리·시간축 34개, 컨테이너 검사 30개로 합계 **186개 통과**다. 이는 오류를 검출하고 잘못된 입력을 거부하는 코드 검사이며 실제 영상 복구 성공이나 모델 성능을 뜻하지 않는다.
