# 공식 모델 전환 2단계 결과 — OLKAVS 단독 실행기

> 작성일: 2026-10-20 · 상위 계획: [공식모델_전환_실행계획_2026-10-20.md](공식모델_전환_실행계획_2026-10-20.md)
> 결론: 영상 파일 하나를 명령 하나로 "입술 추출 → 인식"까지 처리하는 도구를 만들었고, 기존 검증 결과(val20 문자 CER 33.58%·5/20)를 GPU·CPU 모두에서 그대로 재현했다. CPU만 있는 시연 PC에서도 8초 발화를 약 10초 안에 처리한다.

## 만든 것

| 파일 | 역할 |
|---|---|
| [scripts/olkavs_transcribe.py](../scripts/olkavs_transcribe.py) | `roi`(.venv-olkavs-roi) → `infer`(.venv-olkavs) → `run`(드라이버) 세 명령 |
| [backend/tests/test_olkavs_transcribe.py](../backend/tests/test_olkavs_transcribe.py) | 프레임 구간 선택·정규화·NPZ 읽기 단위 검사 5개 (통과) |

검증된 실험 코드를 그대로 import 하고 복사하지 않았다.

- 입술 찾기: `experiments/olkavs_official/automatic_roi.py` (MediaPipe 0.10.21, 외측 입술 20점 + 20% 여백, 640px 검출) + `roi_geometry_step04.py` 의 `stable_context_square` (정사각형·1.5배 문맥·EMA 0.4)
- 인식: `experiments/olkavs_official/verify_model.py` 의 엄격 가중치 검사, `corrected_search.py` 의 hybrid 디코더, upstream commit `af2feda` 고정, 가중치 SHA `f41d7423…` 검사
- 정규화: 발화 전체 float32 평균/표준편차(correction=1), 입력 (1,3,T,96,96) BGR

사용 예:

```bash
python scripts/olkavs_transcribe.py run --video clip.mp4 --out out/clip --device cpu --warmup
```

출력: `out/clip/roi.npz`(입술 프레임), `roi.json`(프레임별 상자·시간), `infer.json`(텍스트·토큰·시간), `result.json`(합본).

## 회귀 검사: 기존 결과와 같은가

| 검사 | 결과 |
|---|---|
| val20 입력(step04 저장 입술 영상 20개) → `infer` 예측 문장 | GPU·CPU 모두 **20/20 step04와 동일** |
| hybrid 문자 CER / 완전 일치 | **33.58% / 5/20** (step04 33.58%) |
| CTC greedy 문자 CER / 완전 일치 | **41.38% / 0/20** (step04 41.38%) |
| 원본 MP4(D: TS1.tar에서 C025_A_006 멤버 추출) → `roi` 42프레임 입술 상자·정사각형 좌표 | step04 trace와 **42/42 프레임 모두 일치** |
| 원본에서 새로 자른 프레임 → `infer` | hybrid "아주 싶으로 감사해" = step04 저장 입력의 결과와 동일 (정답 "아주 싶으고 감사해") |

로컬 AI Hub 자료는 OLKAVS 학습 분포에 포함됐을 가능성이 높으므로, 이 수치는 연결이 올바른지 확인하는 용도다. 처음 보는 사람에 대한 성능은 3단계 팀 웹캠 영상으로 잰다.

## 처리 시간

원본 1920×1080·29.97fps 영상(C025_A_006)에서 세 구간을 잘라 `run` 드라이버로 측정했다. 각 단계는 별도 프로세스이며 모델 로드·예열을 포함한 값이다. GPU는 RTX 3080.

| 장치 | 구간 | 프레임 | 입술 추출 프로세스 | 그중 검출 | 인식 프로세스 | 그중 모델 로드 | encoder | CTC | hybrid | 합계(벽시계) |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| GPU | 발화 1.4초 | 42 | 1.75s | 0.25s | 4.64s | 1.36s | 0.10s | 0.0005s | 0.57s | 6.4s |
| GPU | 3초 | 90 | 2.20s | 0.52s | 4.74s | 1.31s | 0.09s | 0.002s | 0.77s | 6.9s |
| GPU | 8초 | 240 | 3.58s | 1.37s | 9.97s | 1.34s | 0.10s | 0.0002s | 5.80s | 13.6s |
| CPU(4스레드) | 발화 1.4초 | 42 | 1.89s | 0.27s | 4.25s | 1.21s | 0.15s | 0.0001s | 0.42s | 6.1s |
| CPU | 3초 | 90 | 2.35s | 0.58s | 4.58s | 1.21s | 0.31s | 0.0001s | 0.67s | 6.9s |
| CPU | 8초 | 240 | 3.78s | 1.45s | 9.33s | 1.18s | 0.78s | 0.0002s | 4.88s | 13.1s |

val20 20문장 기준 모델 구간만 보면 encoder 중앙값 GPU 0.12s / CPU 0.42s, hybrid 중앙값 2.5s(최대 8.5s, 두 장치 비슷), CTC 0.0002s다. GPU 최대 메모리는 8초 입력에서 590MiB다.

읽는 법
- 시간의 대부분은 **프로세스 시작·모델 로드(약 1.2~1.4초)·검출기 초기화(0.7초)**다. 5단계처럼 상주 프로세스로 한 번만 로드하면 발화당 시간은 "검출(프레임당 약 6ms) + encoder + 디코딩"만 남는다.
- **hybrid 디코딩은 GPU를 써도 빨라지지 않는다.** Python 빔 탐색이 병목이라 길이에 비례해 늘어난다(8초에 5~6초). CTC greedy는 1ms 미만이다.
- 따라서 CPU만 있는 시연 PC도 가능하다. 지연 목표를 맞추려면 CTC 우선, hybrid는 짧은 발화나 선택 모드로 쓴다. 정확도는 hybrid가 낫다(33.58% 대 41.38%).

## 8초 구간 출력 예

같은 영상 1.7~9.7초(문장 두 개 이상 포함)의 출력.

- hybrid: "아주 싶으로 감사해 코로나 때문에 조금 오늘 동생을 많이 줬어"
- CTC: "애주 싶으고 감사 코로나 때문에 주그 모이 송상을 맏이 줬어"

여러 문장이 이어진 입력도 한 번에 처리된다. 다만 이 화자(C025)는 라벨 시각이 영상과 8.36초 어긋나 있어 두 번째 문장의 정답은 여기서 확인하지 않았다.

## 한계

- 입술 검출은 프레임마다 약 6ms이지만 첫 프레임에서 얼굴을 못 찾으면 발화 전체를 거부한다(검증 코드의 규약). 서비스에서는 거부 사유를 사용자에게 보여 줘야 한다.
- `.venv-olkavs-roi`(mediapipe 0.10.21, numpy 1.26)와 `.venv-olkavs`(torch 2.10 cu128, numpy 2.3)는 합칠 수 없어 두 프로세스가 필요하다. 5단계 상주 워커 구조의 근거다.
- WebM(브라우저 녹화) 입력은 아직 시험하지 않았다. 3단계 첫 작업이다.
- 처음 보는 사람·무음 발화 성능은 측정하지 않았다.
